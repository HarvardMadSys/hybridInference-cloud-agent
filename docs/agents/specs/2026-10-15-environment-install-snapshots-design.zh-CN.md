# 环境安装快照设计：新任务不再重复安装

日期：2026-10-15。负责人：Murphy Tian。

状态：已确认，设计与实现在同一个 PR 中提交评审，合并后生效。

修订（同日，#686 合并后的审查修正）：环境测试不再保存快照，改为测试通过后排一次预构建（§4.1、§4.2、§十）；从快照启动时，权限准备只改沙盒用户自己的文件（§5.2）；快照回执必须在运行仍然有效时上报（§4.2）；删除快照会取消它的预构建（§4.2）；host 按本机实际持有的镜像清理（§六）。

设计核对基线：远端 `dev`，提交 `117ca022`。

## 目标

| 场景 | 现在 | 本设计完成后 |
| --- | --- | --- |
| 同一个环境开第二个任务 | 安装脚本从头再跑一遍，最长 15 分钟，agent 等装完才开始 | 从快照建容器，只跑启动脚本（和可选的更新脚本），agent 几秒后开始 |
| 点「测试环境」通过 | 结果用完即删 | 测试通过后自动排一次预构建，之后的新任务直接用 |
| 依赖变了（锁文件改了） | 照常完整安装 | 自动不用旧快照，完整安装，并在后台重新预构建 |
| 对话被恢复到另一台机器 | 安装脚本会重跑（安装记录存在原机器磁盘上） | 不重跑 |

已确定的两点：快照第一版就存 S3，任何机器都能用；快照按锁文件内容失效，另外提供可选的「更新脚本」。

## 一 现状

以下已对照代码确认。

- **每个新工作区都完整安装。** `EnvironmentPreparation.prepare` 在容器里依次跑安装脚本（900 秒上限）和启动脚本（120 秒上限），成功后 agent 才开始第一轮。
- **安装结果都在容器的可写层里。** 仓库在 `/workspace`，依赖目录（`node_modules`、`.venv`、`target`）在仓库里。安装脚本的 HOME 和各工具的包缓存（npm、pip、uv、cargo、go、poetry）都在 `/workspace/.cloud-agent-tools`（`tool_environment()`）。沙盒用户不是 root，写不了系统目录。所以 `docker commit` 能完整带走安装结果。
- **检查点链路已经能用。** #609/#635 能对停止的容器 `docker commit`、只导出新增的层、上传 S3；#658 能在另一台机器上核对、`docker load` 并建容器。
- **环境测试的容器和对话容器是同一种。** `environment_tests.py` 用 `ChatSandboxManager` 和 `ChatSandboxSpec` 建临时组，用对话同样的 `_SourcePrefetch` 导入源码，再跑安装、启动、验证，结束即删。
- **源码导入只会覆盖，不会删除。** `import_archive` 是 `docker cp -` 到 `/workspace`。
- **安装记录按容器 ID 存在 host 磁盘上**（`environment_preparation.py`）。跨机器恢复后容器 ID 变了，新机器上也没有记录，所以下一轮之前会重跑安装。不能重复执行的脚本（建库、跑迁移）会失败，agent 被卡住。

## 二 核心决定

1. **快照只在专用容器里产生**：后台预构建，从不截取用户的对话工作区，也不保存环境测试的容器（§4.2）。这样快照里没有会话和对话数据，不需要冻结正在运行的 Kata 容器，也不会拖慢用户的回合。
2. **快照是安装完成后的容器相对基础镜像的改动，但不含源码。** commit 之前删掉仓库的已跟踪文件和 `.git`，只留下安装产生的东西：依赖目录、缓存、生成的文件。格式和检查点相同，存 S3。
3. **只给严格匹配的新任务用**，匹配条件见 §五。只有同一个 owner 能用；锁文件内容不同就不用。
4. **命中快照的新任务**：从快照建容器 → 导入本任务的源码 → 跑更新脚本（如有）→ 跑启动脚本 → agent 开始。
5. **「安装已完成」的标记写在容器里**，检查点恢复和快照启动都能认出来，不会重跑安装。
6. **快照出任何问题都不阻塞任务。** 退回从基础镜像完整安装，和现在一样。

## 三 方案比较

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| 从用户第一个任务的工作区截取 | 否决 | 带着对话分支和工作区状态；要在运行中的 Kata 容器上 pause 或停机；时机和回合纠缠 |
| 只共享包下载缓存 | 不作为主方案 | 仍要解压、编译、安装，大项目照样要几分钟；以后可以作为补充 |
| **专用容器预构建，快照存 S3（采用）** | 采用 | 内容干净；直接复用检查点链路；任何机器可用 |
| 快照推到 OCI 镜像仓库 | 暂不采用 | 需要多运行一个服务；与恢复设计的结论相同 |
| 快照允许用旧的基础镜像 | 否决 | 新任务会跑在旧镜像上，CLI 和 helper 版本可能与当前 host 不兼容 |

## 四 快照怎么产生

### 4.1 时机

- **环境测试通过**：控制面为测试用的提交排一次预构建（§4.2）。这份安装在同一个提交上已经有可用快照时不排。
- **新任务没有可用的快照**，而环境有安装脚本：控制面自动排一次后台预构建。同一个匹配键（§五）同时只有一个在排队或进行。
- **用户点「重新预构建」**。

同一份安装最近 6 小时内构建失败过，任务就不再自动排预构建，免得一个注定失败的安装脚本在每个任务旁边都在后台再跑一遍；测试通过和用户手动点「重新预构建」不受限制。

S3 没有配置（管理员没开自动快照）时，整个功能关闭，行为和现在一样。

### 4.2 运行方式

预构建复用环境测试的运行记录和领取流程（`agent_environment_runs`），新增 `purpose`：`test` 或 `prebuild`。领取、租约、容量计算、孤儿清理都不变。

- **预构建**：建临时组 → 导入源码 → 跑安装脚本 → 保存快照。只有预构建保存快照。
- **测试**：建临时组 → 导入源码 → 安装 → 启动 → 验证，不保存快照；通过后由控制面排一次预构建（§4.1）。
  - 启动和验证脚本能看到运行期变量，包括 Secret，写出的文件可能带着它们。快照的匹配只看安装指纹（§5.1），运行期 Secret 轮换后旧快照照样会被选中，而新任务的脱敏和发布扫描只认识新值和记录在案的旧值，认不出快照里的那份。所以测试的容器从不保存。
  - 也不能在安装和启动之间保存：保存前要删掉源码，之后就没法继续启动和验证了。
  - 代价是测试通过后要在另一个容器里再安装一次。
- **取消**：用户删除快照、删除环境或点「重新预构建」时，旧快照还在排队或进行中的预构建会被一起取消，与用户取消测试相同：排队的不会再被领取，进行中的在下一次上报时被拒绝并停止。领取时也会跳过快照已经不在构建中的预构建。排队一天仍没有 host 开始的预构建由维护任务放弃：先把快照记为失败，再把这条已经不会被领取的运行记为失败，它不会一直排着，也不会再被自动扩容算作排队中的工作。
- **回执**：只有运行仍然有效时才接受，也就是没有被取消、租约没有过期、没有超过 30 分钟。核对和把快照标为可用在同一个事务里，并锁住运行记录，取消或过期不会夹在两步之间。
- **保存快照的步骤**，由 runner 请 Sandbox Manager 完成，因为 S3 凭据只在 Sandbox Manager 里：
  1. 计算锁文件指纹（§4.4）；
  2. 写入「安装已完成」标记（§七）；
  3. 以沙盒用户身份删掉已跟踪文件和 `.git`；
  4. 停止容器，`docker commit`，导出新增层，上传 S3，与检查点相同；
  5. 本机保留 commit 出的镜像，本机之后的新任务直接用；退役后按 §六 清理。
- Sandbox Manager 只接受带环境测试标签的容器，不会对用户的对话容器做这件事。

### 4.3 存储

- **对象位置：** `cloud-agent/sandbox/env/v1/<sha256(owner)>/<快照 id>.oci.tar`，在现有前缀下，不需要改 IAM 权限。
- **归档里的镜像名：** 固定为 `freeinference-environment/<sha256(owner) 前 16 位>:<快照 id>`。
- **回执：** 和检查点一样，由 host 上报：对象位置、版本、SHA-256、大小、新增层大小、基础镜像、各步耗时。
- **大小上限：** 和检查点共用。超过上限的快照记为失败，界面说明原因。

### 4.4 锁文件指纹

- 预构建时，host 在快照所用的提交里，对已跟踪的锁文件逐个计算 SHA-256，结果记在快照上。
- 「锁文件」按文件名判断：
  - 以安装脚本建议功能（`environment_source.py`）的列表为基础：`package-lock.json`、`pnpm-lock.yaml`、`yarn.lock`、`uv.lock`、`poetry.lock`、`Cargo.lock`、`go.sum`；
  - 再加几种常见的依赖清单：`bun.lock`、`Pipfile.lock`、`requirements*.txt`、`Gemfile.lock`、`composer.lock`；
  - 两处共用同一份列表。
- 子目录里的锁文件也算，这样 monorepo 也能正确失效。数量有上限。

## 五 新任务怎么用快照

### 5.1 匹配

**控制面领取任务时**，如果绑定有安装脚本，就找一份 `ready` 快照，随领取结果一起下发。匹配条件：

- 同一个 owner、同一个环境；
- **安装指纹**相同：控制面对安装脚本和安装期可见的变量名、值计算 HMAC，不存明文，与环境版本号无关。只改了启动脚本或快捷操作时，旧快照照样可用；改了安装脚本、安装期变量或全局变量，指纹就会变；
- **基础镜像 digest** 等于领取方 host 上报的沙箱镜像；
- 快照建好不超过 25 天（§六）。

**runner 拿到快照后**，只在新建组时使用。已有对话的后续回合、从检查点恢复，都不用快照。runner 在 host 上克隆源码之后（现在就在建容器之前做），对本任务的提交计算锁文件指纹：

- 和快照一致：让 Sandbox Manager 从快照建组。
- 不一致：照常从基础镜像建组、完整安装，并告诉控制面「锁文件已变」。控制面按本任务的提交排一次预构建。

没有可用快照时，runner 在导入源码后上报「没有快照」和本任务的提交，控制面按这个提交排一次预构建；同一个环境和指纹，同时只排一个。由 runner 上报而不是在领取时排，是因为领取时任务的提交可能还没确定。

### 5.2 Sandbox Manager 从快照建组

在 #658 `register_manifest` 的「接管现有容器」「新建」「恢复」三条路之外，加第四条：请求带 `environment_snapshot` 时，从快照新建。

1. **本机已加载过这份快照**：按镜像名直接用。同一台机器上的后续任务不再下载。
2. **没有加载过**：按 #658 的步骤处理。按 digest 拉基础镜像；流式下载并核对大小和 SHA-256；检查归档结构，镜像名必须正好是 §4.3 的名字；然后 `docker load`。
3. **建容器**：
   - 启动配置、网络、资源上限、磁盘配额都按 `ChatSandboxSpec` 重新指定；
   - 加标签 `org.freeinference.chat-environment-snapshot=<快照 id>`；
   - 身份校验扩展为：创建时用的镜像，是基础镜像、标签写的检查点镜像，或者标签写的快照镜像。
4. **导入本任务的源码**：和普通新组相同。只是导入前的「清空未完成的首轮」只清 `/agent-state`，不清 `/workspace`，否则依赖会被删掉。重试时再次导入会覆盖同样的源码，结果一致。
5. **权限准备**：导入后，首轮之前会把工作区开放给共享组。它以沙盒用户（UID 10001）运行，只改沙盒用户自己的文件。快照里的安装文件属于安装用户（UID 30000），沙盒用户没有权限改；它们保持安装时的权限，和完整安装时一样（那时安装本来就在这一步之后才跑）。沙盒用户进不去的安装目录直接跳过。

**第 1–3 步任何一步失败**，都删掉这个容器，改从基础镜像新建，任务继续。校验失败（SHA、结构、镜像名）时快照标为 `failed`，不再下发；网络之类的临时错误不改快照状态。

### 5.3 准备与更新脚本

- **安装步骤显示为「使用安装快照」**，带构建时间，不执行安装脚本。
- **更新脚本**：环境新增可选的「更新脚本」，只在从快照启动时运行，放在启动脚本之前。
  - 用安装期的变量，上限 900 秒，与安装脚本相同。
  - 用来处理和源码相关的步骤，比如代码生成、数据库迁移。
  - 失败时和安装失败一样，阻止 agent，可以重试。
- **启动脚本照常运行。**

## 六 失效、清理与配额

- **被取代：** 同一匹配键有了更新的 `ready` 快照，旧的标为 `superseded`。
- **删除：**
  - 环境被删除或归档；
  - 环境有了新版本、或安装期变量指纹变了，旧快照在 24 小时后删除，留出时间给正在建组的任务。发布配置和收到构建回执时都会检查指纹；维护任务也会按当前配置轮流检查每个 owner 的可用快照，每轮 20 个 owner，所以指纹早就变了、环境之后也没再发布的快照同样会停用；
  - 连续 7 天没有被使用。
- **最长使用 25 天：** 快照建好超过 25 天就不再下发；下次用到时照常完整安装，并自动重新预构建。依赖本来也会随时间变旧。
- **谁来删：** 控制面不一定有桶的凭证（归档策略可以不填 access key），所以删除由 host 执行。
  - host 每 10 分钟取一次待删对象，删掉对象版本后回报。最久没尝试过的排在前面，取走一次就算尝试过一次，所以桶拒绝删除的对象不会挡住其他对象。
  - 本地镜像每台 host 自己清：host 列出本机的快照镜像，问控制面其中哪些属于已退役（删除中、已删除、构建失败）的快照，删掉这些。控制面不认识的镜像不动。
  - 删对象需要 `cloud-agent/sandbox/env/*` 上的 `s3:DeleteObject` 和 `s3:DeleteObjectVersion`，这是唯一新增、而且可选的权限。没有这两项权限时，删除失败会被记录并重试，靠下面的生命周期规则兜底。
  - 再在桶上给这个前缀配一条生命周期规则作为兜底：对象创建 30 天后过期。它晚于 25 天的使用上限，不会删掉还在用的快照。规则写进 `docs/developer/operations.md`。
- **每个 owner 的总量上限：** 默认 20 GiB，按最久没用的顺序腾出空间。

## 七 「安装已完成」标记写在容器里

- **标记文件**：`/var/lib/freeinference-broker/environment-setup-v1.json`。和初始归档标记放在同一个目录，目录 0700、属主 root，沙盒用户读写不了，也伪造不了。
- **内容**：安装指纹（§5.1 的 HMAC，由控制面随绑定下发）、写入时的绑定 id，以及快照 id（如有）。
- **何时写**：
  - 安装脚本成功后，由 Sandbox Manager 以 root 写入；
  - 保存快照时，带着快照 id 再写一次。
- **何时读**：host 磁盘上没有这个容器的安装记录时（也就是新建、恢复、换了机器之后），读一次标记，指纹一致就认为安装已完成。
  - **绑定 id 也相同**：这是检查点恢复的同一个工作区。不重跑安装，也不跑更新脚本。
  - **绑定 id 不同**：容器来自快照。安装步骤显示「使用安装快照」，跑更新脚本，然后把标记改成本任务的绑定 id。这样以后再恢复时，不会重跑更新脚本。
- host 磁盘上的记录照旧用来判断「这次启动之后启动脚本跑过没有」，读状态也不用每次进容器。
- 这修复了「现状」最后一条：跨机器恢复后不再重跑安装。

## 八 数据模型

- **`agent_environment_runs`** 新增：
  - `purpose`：`test` / `prebuild`，默认 `test`；
  - `snapshot_id`。
  - 「每个 owner 同时只有一个测试」的唯一索引只约束 `purpose='test'`，预构建不占这个名额。
- **新表 `agent_environment_snapshots`：**

| 字段 | 说明 |
| --- | --- |
| `id`、`user_id`、`environment_id`、`revision` | 归属；版本号只用于显示 |
| `setup_fingerprint` | 安装指纹（HMAC），匹配用 |
| `base_image` | 带仓库域名和 digest 的基础镜像地址 |
| `source_sha`、`lockfiles` | 构建用的提交，以及锁文件路径到 SHA-256 的映射 |
| `object_key`、`object_version_id`、`sha256`、`size_bytes`、`new_layer_bytes` | 存储位置与校验信息 |
| `state` | `queued` / `building` / `ready` / `failed` / `superseded` / `deleting` / `deleted` |
| `run_id`、`host`、`durations_ms`、`detail` | 由哪次运行、哪台机器构建，耗时，失败原因（已脱敏） |
| `created_at`、`ready_at`、`last_used_at`、`use_count` | 用于清理和界面显示 |

  同一环境、同一指纹，`queued`/`building` 的快照同时只能有一个（部分唯一索引），这样预构建不会重复排队。

  `environment_id` 和 `run_id` 不设外键：环境只归档不删除，运行记录也不删除；而且早期迁移的降级会删除这两张表，它们并不知道这张新表。

- **环境版本的脚本文档**新增 `update_script`。它和其他脚本一样存在版本文档里，不需要改表，进入版本历史和差异显示，API 和 OpenAPI 同步更新。
- **绑定**新增 `setup_fingerprint`，在绑定时计算并保存，随领取下发给 host（§七）。

## 九 界面

- **我的设置，环境列表：** 每个环境显示「已预构建 · 2 小时前」「预构建中」或「预构建失败」。行菜单增加「重新预构建」和「删除快照」。
- **编辑器，脚本页：** 新增「更新脚本（可选）」，说明「每次从安装快照启动时运行，用于代码生成、迁移等」。
- **编辑器，测试页：** 测试通过后显示「测试通过后会为这份安装排一次预构建。锁文件不变时，新任务会直接从它开始。」
- **对话的环境面板：** 安装步骤显示「使用安装快照（2 小时前构建）」，后面依次是更新脚本、启动脚本。
- **S3 未开启时：** 环境卡片说明「管理员未开启自动快照，每个新任务都会完整安装」。

## 十 安全

- **只给同一个 owner 用**，不跨 owner 共享。Fork 从源容器复制，与快照无关。
- **快照内容不可信**：它是仓库代码在安装期间写出来的。只有通过 SHA-256、结构和镜像名检查后才交给 `docker load`，与检查点恢复相同。
- **快照里可能有安装期的 Secret**，比如安装脚本写出的 `.npmrc`。处理方式：
  - 匹配要求安装期变量指纹相同，所以拿到快照的新任务，持有的就是同一组值，没有新增暴露；
  - 轮换 Secret 后指纹变化，旧快照停用并删除；
  - 发布扫描照常覆盖这些已知值。
- **运行期 Secret 不进快照**：快照只由预构建产生，预构建只跑安装脚本，看不到运行期变量（§4.2）。早先由环境测试保存的快照不再下发，下次维护时删除。
- **存储凭证**：沿用每台机器已有的归档长期钥匙，和检查点一样，不扩大权限。按对象发临时钥匙是恢复设计第七节的后续工作，届时一并覆盖快照。
- **预构建运行没有推理 grant、MCP 或 Git 写凭据**，与环境测试相同。

## 十一 兼容与上线

- **新能力 `environment-snapshot-v1`。** 没有声明它的 host 不会领到 `prebuild` 运行，领取任务时也不会收到快照。旧 runner 和 Manager 的行为不变。
- **不需要改沙箱镜像。**
- **额外检查：**
  - `make ci-database`；
  - `make ci-frontend`；
  - 在 containerd dind 里跑一遍端到端测试：「预构建 → 另一个 daemon 从快照建组 → 换提交 → 启动」。

**staging 验收：**

1. 准备一个 Node 仓库（`npm ci`）和一个 Python 仓库（`uv sync`），各配一个环境，点「测试环境」。
2. 各开两个新任务。记录第一个回合开始前的等待时间，与没有快照时对比；确认安装步骤显示「使用安装快照」。
3. 改一下锁文件再开任务：确认完整安装，并自动排了新的预构建。
4. 轮换一个安装期 Secret：确认旧快照停用，下一个任务完整安装。
5. 移除一台机器，在另一台机器上恢复一个用了环境的对话：确认安装不重跑。

## 十二 对现有功能的影响

- **导出的后备路径**：没有挂载 containerd 内容存储时，导出改走 `docker image save`。在传统的 overlay2 镜像存储上，它会多带几个镜像并不引用的元数据 blob，加载端的检查会因此拒绝，检查点恢复也一样。实现时改为只写出镜像引用的 blob，`index.json` 也改为直接指向镜像清单；用 containerd 存储的 host 不受影响。
- **没有加密密钥的部署**：安装指纹要用 `AGENT_SOURCE_CONTROL_ENCRYPTION_KEY`。没有这个密钥时，绑定不记指纹，也就不建快照，任务照常创建。

- **初始归档**：新对话在安装之前会把 `/workspace` 存一份初始归档到 S3。从快照建的组，这时依赖已经在了，所以初始归档会变大，和停止时的最终归档相当。最终归档本来就包含安装结果，所以现有的大小上限够用。
- **环境测试**：本身不变；通过后控制面另排一次预构建。
- **检查点恢复**：恢复后不再重跑安装（§七）。

## 十三 风险

- **staging 一天部署好几次，每次基础镜像都会变，快照随之失效。** 生产部署频率低，影响小。以后可以在部署后，为最近 7 天用过的环境自动预构建。
- **第一个任务仍是完整安装**，同时后台多跑一次预构建，占一个容器名额。环境测试通过后同样要再安装一次。
- **大快照下载慢**：机器第一次用某份快照时要从 S3 下载。之后同一台机器直接用本地镜像。
- **安装脚本依赖源码内容**（比如生成代码），锁文件没变但代码变了：需要用户把这类步骤写进更新脚本。界面和文档都要写清楚。
- **S3 费用**：靠 §六 的清理和总量上限控制。

## 十四 不做的事

- 不截取用户对话中的工作区。
- 不跨 owner 共享快照。
- 不允许新任务使用旧的基础镜像。
- 不做 OCI 镜像仓库和层合并（同恢复设计第七节）。
