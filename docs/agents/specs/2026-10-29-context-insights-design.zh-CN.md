# 会话上下文视图与跨会话上下文洞察：设计与实现记录

日期：2026-10-29
状态：已实现，待评审；未部署。参考：[bowenliang123/dsh-context](https://github.com/bowenliang123/dsh-context)

## 一、要解决的问题

用户想知道一个会话的上下文有多大、由什么组成、怎样随请求和轮次增长、什么时候被压缩、哪一步带来了大的变化；
也想跨会话比较这些画像，并能从比较结果直接进入某个会话的上下文视图。用量、费用、缓存命中属于跨会话页面，
但几个汇总数字本身不是这项功能。

本次交付三件事：

1. **会话「上下文」视图**：会话页面「聊天 / 轨迹」旁边新增「上下文」，单个会话的上下文规模、构成估算、
   逐请求增长、压缩事件、最大变化，每一项都能跳到对应的轮次或轨迹步骤。
2. **跨会话「上下文洞察」**：我的设置 → 用量页内，与用量历史共用同一个时间范围，列出范围内每个会话的上下文画像
   （峰值、最近观测、压缩次数、请求数、费用和缓存命中），可排序、分页，点进去就是该会话的上下文视图。
3. **今天 / 7 天 / 30 天 / 全部** 四档范围，前后端都支持。「全部」是这个用户保留下来的全部历史。

dsh-context 运行在 DeepSeek Harness 里面，能读到 Harness 自己组装的每次请求（系统提示词、工具 schema、
每条消息），它的构成也是按「4 字符 ≈ 1 token」估算的。我们的平台看不到 CLI 在沙箱里组装的提示词，
只看到 CLI 流出来、平台存下来的事件。所以这里的每个数字都要说清楚它是哪一种：

| 名称 | 含义 | 来源 |
|---|---|---|
| 请求用量（provider-reported） | 某一次模型请求的输入（含缓存读/写）和输出 token | CLI 转述的服务商用量 |
| 请求上下文大小（observed prompt） | 那一次请求发给模型的全部输入 token（未缓存 + 缓存读 + 缓存写） | 由请求用量算出 |
| 最近观测上下文 | 主 Agent 最后一次请求的上下文大小及时间 | 同上；**不是**此刻的实时占用 |
| 实时上下文占用 | CLI 此刻窗口里实际有多少 | 当前没有任何运行时把它写进事件流，显示「未采集」 |
| 构成估算 | 平台存下的可见内容（用户消息、回答、推理、工具调用、工具结果）按 4 字符/token 估算 | 估算；截断的预览只会少算 |
| 上下文窗口（容量） | 模型窗口大小 | 只有 CLI 报告了才显示；百分比也只在此时显示 |

压缩只来自 CLI 报告的压缩事件。token 下降本身不是压缩证据，视图里也不会把下降标成压缩。

几个细节：

- 输入口径统一成「这次请求的全部输入」：Claude 是 `input + cache_creation + cache_read`；Codex/OpenAI 的
  `input_tokens` 已经包含缓存读；pi 和 OpenCode 的 `input` 是扣掉缓存后的，要加回 `cacheRead + cacheWrite`。
- Codex 会在没有新请求时重发同一份 `tokenUsage`（例如更新速率限制时）；按累计 `total.totalTokens` 严格增长判断是不是新请求。
- OpenCode/Kilo 的原始行只存前 4000 字符。能完整解析成 JSON 的才算观测，解析不了的不猜。
- 新采集只影响部署之后的运行。Claude 的压缩大小和窗口、pi 的压缩，在本版本上线之前的历史里是「未记录」，不是零：视图在对应的数字旁这样写（见 7.8）。

## 三、数据来源与存储

### 3.1 每次尝试一个上下文画像（派生缓存）

沿用 `agent_attempt_thread_stats`（迁移 0099）的做法：事件账本仍是唯一事实来源，新表只是可重建的缓存。

迁移 `0107_attempt_context_profiles` 新建 `agent_attempt_context_profiles`：

- `attempt_id`（主键，级联删除）、`event_seq`（生成时账本最新序号）、`reducer_version`；
- 便于 SQL 排序的列：`main_requests`、`subagent_requests`、`peak_prompt_tokens`、`latest_prompt_tokens`、
  `latest_observed_at`、`context_window`、`compactions`；
- `profile JSONB`：逐请求点、压缩事件、构成估算，有上限（单次尝试最多 2000 个请求点，超出时保留首尾各 1000 个并记下省略数）。

读取时比较账本最新 `seq` 与缓存的 `event_seq` 和版本号，过期才重算。重算按 `seq` 分页读事件，读的是 SQL 里
裁剪过的投影：用量字段、Codex 相关通知、OpenCode 相关原始行，以及正文的**字符数**（`length()`，不传正文）。

### 3.2 会话上下文视图

`GET /v1/agent/jobs/{job_id}/thread/context`：与 `thread/stats` 相同的属主校验（必须是调用者自己的、未删除的会话，
否则 404）。返回：能力说明（每个运行时一份）、最近观测、窗口和百分比（仅在有证据时）、逐轮汇总、逐请求序列、
压缩事件（含压缩前后观测到的请求大小，作为旁证而不是证据）、变化最大的 10 次、覆盖率（有观测的尝试数、子 Agent 请求数、省略的点数）。
每个点带 `job_id / turn_no / attempt_id / event_id`，前端据此跳到轨迹步骤；找不到步骤时打开该轮的运行详情。

### 3.3 跨会话洞察

`GET /v1/agent/usage/context?range=…&sort=…&cursor=…`：选「范围内创建的轮次」（`job_created_at`，与用量历史同一口径，
排除 Fork 复制的历史轮次），按会话分组，用画像列在 SQL 里聚合，键集分页（每页 25）。排序：最近活动、峰值上下文、压缩次数、请求数。

画像是懒生成的。每次请求最多补算有限数量的尝试（尝试数和事件数双上限），写回缓存后返回
`profiling.pending`；还有未补算的尝试时，页面说明「排名尚未完整」并自动再取，直到全部补齐。不会把没补算的当成零，
也不会因为补不完就缩小范围。

每页会话的费用和缓存命中由服务端用现有 Gateway 用量汇总按会话求和（`AdminUsageQueries` 增加按会话过滤），
浏览器不做金额加法。

### 3.4 范围与「全部」

- 时区：UTC 自然日，与现有用量页和 Gateway 每日额度一致。界面标注「UTC」，并给出今天的 UTC 起点对应的本地时间。
- 今天 = 当前 UTC 日 00:00 到现在；7 天 / 30 天 = 含今天在内的最近 7 / 30 个 UTC 日；
  全部 = 从这个用户最早一条保留记录（最早的轮次或最早的容器，取更早者）所在的 UTC 日到现在。
  `/tokens`、`/resources`、`/context` 共用同一个解析函数，返回同一个 `range` 描述。
- 资源保护靠分批，不靠截断：
  - 用量汇总按 `(created_at, id)` 键集分批，每批仍受原有的运行数、账本行数、快照字节预算约束；
    所有批次在同一个只读可重复读事务里，逐批归并（精确十进制，未知保持未知）；整次读取有总时限，
    并发的多批读取受进程内信号量限制。超时返回 503，不返回部分和。
  - 柱状图分桶由服务端决定：不超过 92 个桶按日，否则按 ISO 周（周一起，UTC），超过 156 周按月。
    浏览器不合并桶，也不做金额加法。
  - 用户接口同样检查响应字节上限。

## 四、界面与验收

**会话「上下文」视图**（会话页标题栏「聊天 / 轨迹 / 上下文」）：

- 顶部：最近观测上下文（附时间、轮次、模型）；有窗口证据时显示占比条，否则写「窗口大小：此运行时未报告」；
  实时占用一栏明确写「未采集」及原因；最近观测之后若有压缩，标「已压缩，此观测早于压缩」。
- 增长图：每个请求一根柱（可切换按轮），压缩事件用标记钉在发生的位置；点柱子打开对应轨迹步骤。
- 构成估算：最近一次压缩之后的可见内容按类别估算，旁边是「无法从存储内容归因」的部分（系统提示词、工具 schema、
  被截断或不可见的内容），只有观测值大于估算时才显示差额。
- 压缩事件列表、变化最大的请求列表、逐轮表格，每一行都能跳转。
- ~~能力说明~~：已删除（见 7.8）。估算、最近观测、未记录等说明只写在对应的数字旁边。

**用量页「上下文洞察」**：范围由用量页唯一的范围选择决定（今天 / 7 天 / 30 天 / 全部，见 7.7）、范围说明（UTC 起止）、
上下文汇总（有观测的会话数、请求数、压缩次数）、会话画像表（标题、运行时与模型、
峰值和最近观测与窗口的对比条、压缩、请求、费用、缓存命中、覆盖说明），点标题进入该会话的上下文视图。

**验收**：空数据、部分覆盖、多轮、压缩、多模型、长历史（「全部」超过原有 1 万次运行上限）、窄屏，
在本机用合成数据预览并截图；测试覆盖属主隔离、范围与「全部」超出旧上限、汇总正确与未知值、
逐会话跳转与数据归属、上下文语义（不把下降当压缩、不把最近请求当实时占用）。

## 五、不做的事

- 不改 Gateway，不读 Gateway 密钥；没有 Gateway 合同缺口（用量与费用已经由现有合同提供）。
- 不做 Fleet / 多 Agent 编排页面，不编辑系统提示词，不做新插件平台。
- 不采集 Claude `get_context_usage` 和 pi `get_session_stats`：两者都需要在常驻会话里插入额外的控制请求并处理其回复，
  会占用对话自己的通道、拖住回合结算（Claude 还会调用 `count_tokens`），所以不询问，见 6.1。

## 六、续：单次请求的上下文构成（2026-10-29 第二部分）

第一部分的"构成估算"把上次压缩之后存下的全部文本加在一起，回答不了"某一次请求里到底有什么"，还用"最近请求减估算"
的差额暗示系统提示词和工具定义占了多少。第二部分改成**按请求**展示，三种来源分开标注：

1. **服务商报告的输入**：这次请求的输入 token（精确值）；缓存读取/写入只是同一份输入的计费拆分，不另加。
2. **CLI 自己的统计**：只用不占用对话的读取，从不在轮次结算路径上询问 CLI。OpenCode/Kilo 由沙箱里的 bridge
   在轮次开始时（`prompt_async` 被接受后），用自己的线程通过服务端回环 HTTP 读取这一轮**第一次请求**发送的内容，
   作为 `context_snapshot` 生命周期事件存下（类别、来源名、大小估算、短预览；不存整段内容）；Claude Code 只用它
   每轮启动行（`init`）里已经报告、已经存储的工具菜单和 MCP 服务名，没有大小。同一轮后面的请求会注明
   "读取早于这次请求，此后本轮已有 N 次请求"，本轮在读取之后发生压缩也会注明；这些都不是实时占用。
3. **根据存储内容重建**：按记录顺序挑出这次请求之前的存储内容——各轮提问、回答、推理、工具调用与结果、压缩摘要；
   去掉压缩之前的内容、被重试替换的尝试、子 Agent 自己上下文里的内容、这次请求自己的输出（Claude/pi 按 `usage_id`，
   Codex/OpenCode 按"上一次用量报告之后的助手内容"）。这是重建，不是实际组装的请求：CLI 自己加入的系统提示词、
   工具定义、指令不在其中，预览可能被截短，大小是估算。每一项可以展开看存储的原文（分段读取，属主校验），
   或跳到对应的轨迹步骤。

不再用两个总数相减来推断某个类别的大小。

### 6.1 各 CLI 的接口核对（固定版本）

上下文统计不能影响对话：最终输出、轮次结算、后续轮次的接纳与执行、取消、resume 与 fork 都不等待它，不增加推理请求，
也不在每轮强制向服务商发起计算 token 的请求。第一版曾在轮次结算后通过对话自己的 stdin/stdout 询问 Claude
（`get_context_usage`）、pi（`get_session_stats`/`get_messages`）和 bridge（`context` 命令）；结算因此要等待回答
（Claude 最多 20 秒、并约 18 次 `/v1/messages/count_tokens`；pi 与 bridge 的读取没有超时），bridge 的 stdin 循环
在读取期间也会把下一轮或中断排在后面。这些询问已全部移除。

| 运行时 | 核对的接口 | 结论 | 实现 |
|---|---|---|---|
| Claude Code 2.1.220 | stream-json 控制请求 `get_context_usage`（真实 2.1.220 二进制对本机假 Messages API 实测） | 能回答系统提示词、工具、MCP、记忆文件、技能和消息拆分，但只能在对话自己的通道上询问，且回答时 CLI 会调用约 18 次 `count_tokens`（端点不支持时本地估算） | **不询问**。改用每轮 `init` 行里已存储的工具名与 MCP 服务名（`harness`），标为"只有名称，没有大小"；系统提示词、指令、技能标为不提供 |
| Claude Code 2.1.220 | `compact_boundary` 之后的合成 user 消息 | 就是压缩摘要正文 | 照旧存为 `compaction_summary` 生命周期事件（最多 4000 字符） |
| pi 0.73.1 | RPC `get_session_stats`、`get_messages` | 只能在对话自己的 RPC 通道上询问；`get_messages` 是单行 JSON | **不询问**，能力表为"不报告"；完成的压缩照旧记录 `summary_text` |
| OpenCode 1.18.9 / Kilo 7.4.17 | `GET /session/{id}/message`、`GET /experimental/tool?provider&model`（服务端回环 HTTP，只读，不调用模型） | 按 `filterCompacted` 得到请求携带的消息与工具定义；系统提示词没有接口 | bridge（helper pin `5`）在轮次开始时用独立线程读取：截到本轮提示（按文本与创建时间匹配，最多轮询 10 次、每次 0.2 秒），每次 GET 5 秒超时、8 MiB 上限，最多 300 项、每项 160 字符预览；只在该轮仍在进行时、在与 `settled` 相同的锁下写出，否则丢弃并只写 stderr 诊断；同一时间只有一个读取。主机不发送任何命令，也不等待 |
| Codex 0.145.0 | app-server v2：`thread/read` 只返回界面条目；模型可见内容只能通过内部实验接口获得 | 没有受支持的接口 | 不启用实验接口 |

### 6.2 token 估算

项目依赖里没有各服务商的分词器。估算规则（`cloud_agent_shared.text_tokens`，Postgres 中按同一规则计数）：
ASCII 每 4 字符 1 token，CJK（中日韩字符、全角）每字符 1 token，其他非 ASCII 每 2 字符 1 token。
代码按 ASCII 计，标点密集的代码会偏少；截短的预览会偏少。Claude 的名称没有大小，界面不显示数字。

### 6.3 历史与覆盖

OpenCode/Kilo 的读取只对使用新 bridge 的运行存在；读取被丢弃（慢、太大、轮次已结束）时不写任何内容。没有统计时说明原因：

- `not_offered`：这个运行时没有不占用对话的读取（pi、Codex）。
- `pending`：这一轮还在运行，读取结果还没到。
- `not_settled`：这次尝试在读取到达之前被重试、失败或被取消。
- `not_collected`：已结束的一轮没有读取结果：早于采集，或读取被丢弃。

Claude 的名称来自启动行，早于本功能的运行也有。重建结果在所有情况下照常可用。压缩边界之前的内容一律算作"已压缩"，但各 CLI
都可能把最近的一部分带过压缩（Claude 的 `preserved_segment`、pi 保留的最近消息、OpenCode/Kilo 的 `tail_start_id`、Codex
保留的最近用户消息），存储的转录说不清是哪些，所以界面注明重建结果可能比实际请求少。能力表"CLI 自己对请求的统计"一行：
OpenCode/Kilo 为"从这个版本起有报告"，Claude 为"只有工具和 MCP 名称，没有大小"，pi 与 Codex 为"不报告"，并给出
"N 轮中有 M 轮读到"。属主校验：组成与原文读取都要求会话属于调用者且未删除，原文只返回平台存储时已经脱敏的文本。

## 七、续：与 dsh-context 的能力对齐（2026-10-29 第三部分）

参考 dsh-context 的 Context Insights、Context Events、侧栏、`/context` 与 Context browser，按本应用已有的数据契约实现，
不照搬它的 API。统计一律不进入对话的关键路径（见 6.1）：不询问 CLI、不增加推理或 `count_tokens` 请求；
新证据只来自平台自己已经掌握的信息（认领时对提示词的包装）和 CLI 本来就写到流里的内容。

### 7.1 数据来源与口径

| 指标 | 来源 | 口径 |
|---|---|---|
| 活动热力图 | 范围内的运行（`agent_jobs.created_at`，UTC 日，与用量历史同一归属规则）+ 尝试画像 | 每个有运行的 UTC 日：轮次、会话数、主 Agent 请求数、压缩次数、最大请求。只在第一页返回，覆盖整个范围，不受「按日筛选」影响（用户正是从它里面挑日期）。「全部」不截断：浏览器一次画 26 周，写明画的是哪几周，可以向前后翻；上面的合计始终是整个范围 |
| 跨会话构成 | 服务端返回两组数字，从不相加或相减。①**记录的内容（估算，`chars_cjk_v1`）**：每轮保留的那次尝试（被重试替换的不算）里存下的每一项只算一次，加上每轮的提问（`task_prompt`）和平台认领时加入的内容；子 Agent 自己的上下文不算；Fork 复制来的轮次归原会话。②**服务商报告的请求输入（精确）**：每次请求的输入按 CLI 转述的服务商用量求和，包括被重试替换的尝试（这些请求确实发出过），子 Agent 单列。会话保留的内容每次请求都会再带一遍，所以②是「逐请求暴露量」，自然比①大。界面只画①；②属于用量层面的数字，由「历史用量」呈现，洞察里不再单独汇总（见 7.7） | 系统提示词和工具定义从未存储，没有对应类别，也不用差额去推算。被截短的记录让①偏少，界面写明有几轮如此；①注明不是计费用量 |
| 搜索 / 项目 | 标题或仓库名，不区分大小写的子串（≤200 字符；会话列表只搜标题，这里多搜仓库名）；项目就是会话的 `repo`，`repo IS NULL` 单独作为「无仓库（临时工作区）」一组 | 服务端在整个范围上先筛选，再排序、分页；游标绑定范围、排序、搜索、项目和日期，换了条件的旧游标返回 422；属主条件在每条 SQL 里 |
| 上下文事件 | 尝试画像里的事件列表（派生缓存，随账本增量刷新，不另读一遍事件） | 见 7.2 |

洞察的每条语句都带可选筛选条件（`$n IS NULL OR …`）。同一连接上同一预备语句执行五次以后，Postgres 可能改用通用计划；
在 12,000 次运行的历史上，构成查询因此从 0.1 秒变成 19 秒、超时。读取时用 `plan_cache_mode = force_custom_plan`
（刷新阶段结束即 `RESET`，快照内用 `SET LOCAL`），连接放回池里时不留任何会话状态。
构成查询还按「每次运行」用索引查找它保留的尝试和全部尝试的请求合计，再按会话汇总，不把整段范围的集合互相连接：
范围内的运行常被低估（刚写入还没有统计信息，或者只是某个用户在整张表里的一小部分），估成 1 行时，Postgres 会选嵌套循环，
对另一边的每一行都重新扫一遍整个集合。10,250 次运行、只有 `agent_attempts` 有统计信息时，原来的写法要 4 秒（CI 上超过 5 秒的超时），
每个尝试都有画像时超过 1 分钟；现在不论统计信息处于什么状态都是 0.2–0.7 秒，结果逐行相同。
这样写之后，每次运行的查找被逐行计价，范围一长，估算成本就会越过 `jit_optimize_above_cost`：服务自己的连接池本来就关闭 JIT
（`bootstrap/lifespan.DATABASE_SESSION_SETTINGS`），测试用的连接池却保留服务器默认值，编译反而比执行还慢（10,250 次运行上 0.61 秒里占 0.37 秒），
在 CI 这种又小又忙的机器上超过了 5 秒。所以洞察的读取自己关闭 JIT（与 `plan_cache_mode` 一样，结束后复位或用 `LOCAL`），
并把每次运行的成本降到必要的部分：一次扫描该运行的尝试，同时得到保留的那次和全部尝试的请求合计；纯 ASCII 的提问（绝大多数）
不再做两次字符类替换（结果恰好是 ASCII 字符数、CJK 为 0）；按会话分组用字节序（与数据库排序规则对 id 的分组完全相同）。
同样的数据上，CPU 限到 0.25 核时从 2.7 秒降到 0.4 秒，结果逐行相同。
真正让 CI 超时的是所有洞察语句共用的「范围内的运行」：运行与会话的连接里，`t.deleted_at IS NULL` 恰好匹配部分索引
`idx_agent_threads_archive_history (user_id, archived_at, id) WHERE deleted_at IS NULL`。批量写入后 autovacuum 已经对会话表做了
VACUUM ANALYZE（行数已知、可见性映射全满，仅索引扫描显得几乎不要钱），列统计信息却还没有，`IS NULL` 按默认选择率估成十几行；
运行又被估成 1 行，于是对每次运行都把这个索引从头走一遍，按 id 在索引内部过滤。计划里每次循环只显示 1 行，看不出是平方级。
10,250 次运行上，每条用到它的语句要 1.1–1.3 秒，整个洞察读取要 7 秒（本机），CI 上超过 5 秒。现在每次运行的会话放在
`OFFSET 0` 隔开的子查询里按主键读取，会话的过滤条件放在外面，部分索引不再可选：每条语句 70–160 毫秒，整个读取 0.8 秒，结果相同。

### 7.2 上下文事件（Context Events）

| 类型 | 证据 | 大小 |
|---|---|---|
| 注入 | ① 平台认领时对提示词的包装（附件说明、长期记忆、所选技能、SSH 服务器、目标前言）：认领响应里带上每一项的来源、条数、字符数（含 ASCII/CJK 计数），runner 写进本来就要写的 `started` 生命周期事件，不存正文；插件只列名称，大小平台看不到。② CLI 写到流里的合成内容：Claude 非回放、非工具结果的 user 行（技能正文、`isMeta`/`isSynthetic`），pi 扩展的 `custom` 消息，OpenCode/Kilo 用户消息里标记 `synthetic` 的文本 part | 字符数换算的估算，标为估算 |
| 压缩 | 已有的压缩记录 | 只显示 CLI 报告的前后大小（Claude `pre/post_tokens`、pi `tokensBefore`），否则写「CLI 没有报告大小」 |
| 修剪 | Kilo 在请求过大前把旧工具输出标记为 `time.compacted` 后重发的 tool part（以前会被误存成一次新的工具结果） | 被清除输出的字符数 |
| 切换模型 | 平台记录的每轮模型；pi 每次请求报告的模型 | 无 |
| 模式变化 | Claude 的 `EnterPlanMode`/`ExitPlanMode` 工具调用，以及启动行 `permissionMode` 与上一轮不同时 | 无 |

存储预览被截短不是修剪；无法解释的 token 升降不推断为任何事件。被重试替换的尝试里的事件照样列出、标明、不计数；
Fork 复制来的轮次标明「复制」；子 Agent 自己的注入和修剪不算会话的。视图最多列 500 条，其余计数并说明。

各运行时不能显示某类事件时，给出具体原因（固定版本核对，证据在交付目录 `ref/`）：

| 运行时 | 注入 | 压缩 | 修剪 | 切换模型 | 模式 |
|---|---|---|---|---|---|
| Claude Code 2.1.220 | 部分：平台注入 + CLI 合成 user 行，自本版本起 | 有 | 无：CLI 内部「按时间微压缩」清除旧工具结果，只写分析日志，不写流（`microcompact_boundary` 只在交互界面里被渲染为空） | 有（每轮设置） | 部分：计划模式工具调用与启动模式；CLI 内部切换的模式不在流里 |
| Codex 0.145.0 | 部分：只有平台注入，CLI 注入的内容不在流里 | 有 | 无对应记录 | 有（每轮设置） | 不适用：平台固定模式，流里没有模式记录 |
| pi 0.73.1 | 部分：平台注入 + 扩展 `custom` 消息，自本版本起 | 有 | 无对应记录 | 有（每次请求） | 同 Codex |
| OpenCode 1.18.9 | 部分：平台注入 + 发布到事件流的 `synthetic` part，自本版本起（计划模式提醒等只加在内存请求里的 part 看不到） | 有 | 不发生：`compaction.prune` 默认 false，平台配置没有开启 | 有（每轮设置） | 同 Codex |
| Kilo 7.4.17 | 同 OpenCode | 有 | 部分：请求过大前的修剪能看到；一轮结束后的修剪需要 `compaction.prune === true`，平台没有开启 | 有（每轮设置） | 同 Codex |

### 7.3 界面

- 设置 → 用量 → 上下文洞察：搜索框（服务端搜索整个范围，停止输入 300 毫秒后发出）、项目下拉（含「无仓库」）、
  「按项目分组」（每个项目在整个范围与当前搜索下的会话数、轮次、请求、压缩、最大请求，点开即按该项目筛选）、
  每日活动热力图（悬停/聚焦显示当日数字，点击按日筛选，再点或点筛选标签取消）、构成图（只有记录的内容，见 7.7）、
  每个会话一条记录内容构成条。
- 会话「上下文」视图：新增事件时间线（按类型筛选与计数、来源、时间、轮次/步骤链接、只在有证据时给出大小）；
  单次请求的内容浏览器增加文字搜索和「从大到小 / 按对话顺序」。
- 「上下文」只有一个入口：会话页顶部与「聊天」「轨迹」并列的主视图。右侧工作区（Git、Terminal、Files、环境、侧聊）
  里没有「上下文」标签（见 7.6）。
- `/context`：斜杠菜单里与 `/goal` 并列，可用方向键选择。在会话里切换到主区域的「上下文」视图，不打开、不关闭、
  也不切换右侧工作区；新建任务（还没有会话）时弹出说明并链接到上下文洞察。不发送消息、不调用模型、不消耗轮次，
  不改模型和运行时；命令后面的文字留在输入框，回到「聊天」时还在。
- 主视图和 `/context` 共用一份数据：会话页上的提供者只在「上下文」视图显示时读取、在轮次进行中每 5 秒轮询一次；
  换到另一个会话时先丢弃旧数据，绝不在新会话下显示旧会话的内容。

### 7.4 验收

组合筛选（范围 × 搜索 × 项目 × 日期 × 排序 × 分页）、属主隔离、构成计算与覆盖、事件语义、`/context` 不提交、
切换会话不串数据且草稿保留、工作区没有「上下文」标签（含旧的已保存选择）、「全部」的大历史（含预备语句通用计划回归）、
窄屏与中文界面。

### 7.5 与 dsh-context 的差距

dsh-context 运行在 Harness 内部，能读到每次实际组装的请求；本平台读不到，所以：实时上下文占用、系统提示词与工具定义的大小
仍为「未采集」（6.1）；Codex 没有受支持的读取接口；Fleet 等与上下文无关的插件功能不在范围内。这些不能算作已对齐。

### 7.6 修订（2026-10-30）：「上下文」的位置

第三部分最初按用户当时的要求，把「上下文」做成右侧工作区面板里的一个标签（与 Git、终端、文件、环境并列），
`/context` 打开这个面板，面板里另有链接打开主区域的完整视图。之后用户改了要求：「上下文」必须和「聊天」「轨迹」
处在同一层导航，不能放在工作区标签里。现在的实现以此为准：

- 工作区标签只剩 Git、Terminal、Files、环境和侧聊；面板版的「上下文」及「打开完整的上下文视图」已删除。
- 浏览器会话存储里如果还留着以前选中的工作区「上下文」标签，读取时回到 Git，其余已保存的标签（如侧聊）不变。
- `/context` 只切换主区域到「上下文」，其余行为见 7.3。
- 原先放在面板里的仪表盘（Token 统计、耗时统计、窗口卡片、上下文趋势、上下文浏览器）全部留在主视图里，
  按主区域自身宽度排版：760 px 起两栏，600 px 起上方两张统计卡并排，更窄时单栏。

### 7.7 修订（2026-10-30）：用量页只有一个范围，洞察只看上下文

用量页原来在「历史用量」和「上下文洞察」两张卡片上各放一个范围下拉（共用同一个状态），洞察的构成图里还有一栏
「服务商报告的请求输入（精确值）」，汇总了全局的输入、输出和缓存读写，和历史用量重复。用户确认的方向是：
全局消耗留在原来的历史用量里，上下文洞察只做上下文分析。现在：

- 范围下拉只有一个，位于「容器」之下、两张卡片之上，写明它作用于历史用量和上下文洞察；上面的容器是实时状态，
  不按日期筛选。默认仍是 7 天，四档与「全部」的含义不变。两张卡片读同一个范围，各自不再有范围控件。
- 换范围时，洞察里从热力图选中的日期在同一次渲染里清掉，不会有一次请求带着新范围和旧日期。
  搜索、项目、分组和排序只属于洞察，不影响历史用量的读取。
- 历史用量不变：费用、输入/输出 token、缓存命中率、推理 token、容器运行时间、CPU 与内存、可切换指标的趋势图、
  按模型表和覆盖说明。
- 洞察的构成图只画记录的内容（估算），并注明这不是计费用量、服务商报告的 token 与缓存命中见历史用量。
  会话行仍保留各自的费用和缓存命中两列。服务端的 `composition.provider` 字段和 API 不变，前端不再展示它的汇总。

### 7.8 修订（2026-10-30）：会话「上下文」视图不再有「各 Agent 报告的内容」

用户要求把会话「上下文」视图底部的「各 Agent 报告的内容」一节（逐运行时的能力表）和它下面的诊断说明
（有观测的运行数、没画出来的较早请求、截得太短的记录、没有结果的压缩）整个删掉，不折叠，也不挪到别的标签页。

压缩「CLI 没有报告大小」、事件一节自己的「哪些事件看不到」。接口的 `capabilities` 和 `coverage` 字段、采集逻辑、
图表、事件、导航和用量页都不变。
