# 精简 `.env`：网页能管的都不留在 `.env`

- 日期：2026-11-03
- 依据：[环境变量盘点与门禁](2026-10-29-env-inventory-and-gates.zh-CN.md)；HybridInference 的
  数据库配置设计（`docs/agents/specs/2026-10-10-db-backed-config-first-run-setup-design.md`）
- 取代：#1057 的统一配置管理方案（部署代理、Deployment 页面、密钥轮换和换库流程）。原因见第 6 节。

## 1. 要解决的问题

部署者面对的 `.env` 又长又乱：控制面的 `.env.example` 有 45 项，自管主机有 49 项。很多项其实早就不靠
`.env` 了，比如 SMTP、沙箱归档、网站地址、沙箱资源上限。它们已经是数据库设置，`.env` 里的值只在首次启动时
导入一次，之后改了也没用；可示例文件和文档还在列它们，部署者分不清哪一行真正起作用。

目标：**`.env` 只放启动前必须知道的东西；其余配置都在 Admin 里改。**

## 2. 原则

1. **`.env` 只留三类值**：
   - 读数据库之前就要用的：数据库连接、设置根密钥、账户会话密钥、`ADMIN_TOKEN`；
   - 容器之间怎么连：网络名、端口、网页路径、compose 参数、部署版本号；
   - 主机自己的接线和边界：接入令牌、隧道、本机目录、沙箱镜像，以及 AGENTS.md §7 规定只能在本机
     决定的沙箱隔离和网络范围。
2. **数据库为准**：一项配置注册成设置后，首次启动从环境变量导入一次，之后以数据库为准。这套机制
   （`MIGRATED_SETTINGS`、主机设置的 `settings_imported`）已经有了，本次只补漏，不新造。
3. **主机的设置走心跳**：所有服务器统一的值在 Admin → Settings 设置，单台服务器的在 Servers 页面设置，
   主机在下一次心跳时拿到。不在主机上装新的常驻程序。
4. **不靠记性，靠门禁**：分类表给每个环境变量一个归属，测试保证新变量必须归类，示例文件不能再写网页能管的项。

## 4. `.env` 去留

**控制面必填（9 项）**：`AGENT_DATABASE_URL`、`AGENT_POSTGRES_PASSWORD`、`AGENT_SETTINGS_ENCRYPTION_KEY`、
`AGENT_LOCAL_SESSION_SECRET`、`ADMIN_TOKEN`、`AGENT_DEPLOYMENT_SHA`、`AGENT_WEB_BASE_PATH`、
`AGENT_WEB_API_URL`、`AGENT_NETWORK_NAME`。

**控制面升级后可删**：`AGENT_WEB_BASE_URL`、`AGENT_SMTP_*`、`AGENT_LOCAL_ADMIN_EMAILS`、
`AGENT_SANDBOX_ARCHIVE_S3_*`、`AGENT_MAX_STREAMS_PER_USER`、`AGENT_API_DOCS`、`AGENT_RUNTIME_REGISTRY_URL`。
网站地址没填时，Admin 页面顶部已有的「需要完成设置」提醒会点名。

**主机升级后可删**：`AGENT_HOST_SLOTS`、`AGENT_SHARED_RESIDENT_CAPACITY`、`AGENT_SANDBOX_CPU_MILLICORES`、
`AGENT_SANDBOX_MEMORY_MIB`、`AGENT_SANDBOX_DISK_MIB`、`AGENT_CHAT_IDLE_TIMEOUT_S`、`AGENT_SOURCE_IMPORT_MAX_MIB`、
`AGENT_LEASE_TTL`、`AGENT_RUNTIME_REGISTRY_URL`、`AGENT_GIT_AUTHOR_*`。脚本和 compose 对这些都有默认值。

**保留**：
- `AGENT_COMPUTE_SECRET_KEY`：它其实也是数据库设置（`compute_encryption_key`），首次启动导入后，compute 凭据
  都用数据库里那把解密，`.env` 里的值不再起作用（升级演练里换成别的值，凭据照样能解开）。但 `deploy.sh`
  发现这一行没有就会写一个新的随机值，删了也会被补回来，所以留着；
- 主机的 `AGENT_SANDBOX_MANAGER_TOKEN`：主机自己的那份凭据。

**留在 `.env`、但这次没动的**：性能剖析开关（`MODE` 是部署的上限，盘点里定为部署配置）、pgAdmin 首次设置、
隧道和沙箱网络。它们要么属于部署边界，要么要另做设计，见第 7 节。

## 5. 生效提示

只在需要人做事时才提示：
- 缺少必填设置：Admin 页面顶部已有提醒（`setup_status`），本次不改；
- 需要重启才生效：目前只有两项（`AGENT_MCP_ALLOW_PRIVATE_TARGETS`、`AGENT_MCP_ALLOW_PLAIN_HTTP`），它们的
  说明里已经写明要重启 MCP 监听程序。

「哪些进程已经用上新设置」这种全局状态条要靠每个进程上报（#1057 的 WP4），本次不做：只为两项设置引入
一张实例上报表，得不偿失。

## 6. 为什么不用 #1057 的做法

#1057 把「尽可能多的配置能在前端管理」理解成「369 个环境变量都要有前端管理方式」。按它自己的分类，
`.env` 里的大部分项属于「应用」：值继续留在 `.env`，由每台机器上的部署代理远程改写。这样 `.env` 一行没少，
机器上反而多了代理的目录和要手写的 `policy.json`；而为了从网页安全地改密钥和数据库地址，又引出了轮换、
探针、维护模式和换库流程，最后成了一个普通管理员看不懂的 Deployment 页面。

本设计只做能让 `.env` 真正变短的事：搬进数据库，或者从示例文件里拿掉。

## 7. 以后可以继续做的

- `AGENT_HOST_CAPACITY_ENABLED`、`AGENT_HOST_STORAGE_PROBE`：可以做成主机设置。存储探测要和主机脚本的校验
  对齐，需要单独设计。
- 性能剖析的 `ENABLED`/`RUN`/`SINK`：可以做成设置，但 `MODE` 作为部署上限要留在本机。
- 「需要重启」的全局提醒：等需要重启的设置多起来再做进程上报。
- 首次安装自动生成密钥（设置根密钥、账号会话密钥、数据库口令等），已有值一律复用；只能在全新安装时生成，
  因为老部署可能靠 `AGENT_SESSION_SECRET` 兜底，没有设置根密钥那一行。同一个 PR 里让 `deploy.sh`
  在数据库已有 compute 密钥时不再补写这一行，并改正 `docs/developer/operations-compute.md` 的说法：
  备份时要和数据库一起保管的是设置根密钥，compute 密钥已经随数据库走。
