## 目标

机器会到期、会被缩容、会突然死掉，但用户感觉不到背后换了机器。按开放生产的标准设计。

| 场景 | 现在 | 本设计完成后 |
| --- | --- | --- |
| 空闲时机器突然死了 | 管理员只能移除这台机器；上面的对话再发消息会一直排队 | 下一条消息多等一会儿（从 S3 取回），对话和代码都在（第一版） |
| 计划内换机器（到期、缩容、升级） | 只有整机搬家一条路；扩缩容开出来的机器不能搬，到期就丢 | 完全无感：沙箱提前在别的机器上准备好（第一版之后） |
| 一轮跑到一半机器死了 | 这个对话标为 `lost` | 明确告诉用户这一轮被中断，回到上一轮结束时的状态，用户可以一键重跑（以后） |
| 机器被攻破 | 拿到所有机器共用的长期 AWS 钥匙，能读所有人的快照 | 只能碰到这台机器上正在运行的那几个沙箱（以后） |

原先第四行"打开自动快照后机器宕机或 Manager 异常重启，沙箱会被锁住"，已经由 [#599](https://github.com/HarvardMadSys/hybridInference-cloud-agent/pull/599) 改为跳过那次 final 归档，不再锁住。只有跳过标记写不进去、或者还没收到任何策略时，才仍然锁住。

## 一 现状（2026-10-14）

以下均已对照代码或 staging 确认。

**沙箱绑定在机器上。**

- `agent_sandboxes.host` 是非空字段。后续回合的领取条件是 `s.host = <领取方主机>`（`storage/repositories/attempt_commands.py`），所以一个沙箱组只能在它所在的机器上继续。
- 管理员"移除机器"（`POST /admin/agent/runner-hosts/{host}/remove`）会做两件事：
  - 吊销这台机器的凭证；
  - 强制移除时，同一事务里让它的租约立即过期。正在执行、结果不确定的那一轮会标为 `LOST`。

  这台机器上停着的组没有任何变化：领取条件仍然要求原机器，所以新消息只能排队，直到同名机器重新注册。

**检查点已经在保存，但只存不取。**

- 只要打开了自动快照，每次正常停止都会存检查点（默认打开）。流程：
  1. 对停止的容器执行 `docker commit`；
  2. 从 containerd 的内容存储里取出新增的层，打成 `docker load` 能读的 OCI 归档；
  3. 上传到 `cloud-agent/sandbox/v2/<sha256(沙箱 id)>/g<generation>/<检查点 id>.oci.tar`。
- 回执随心跳上报，记入 `agent_sandbox_checkpoints`，状态是 `reported`。控制面只在回执写的 host、generation、容器 ID 都和当前一致时才记录。
- **回执没有和具体某一次停止绑定。** 组停止、存了检查点、之后又启动并停止，如果第二次检查点失败了，最新的回执仍然是第一次的，控制面分不出它已经过时。第一版必须先补上这一点（6.2）。
- 现在没有任何代码读回执来恢复。
- staging 当时有 89 个停着的组，其中只有 2 个有当前 generation 的检查点。大部分组建于检查点上线之前。

**沙箱基础镜像。**

- 每个容器都记着自己的基础镜像，标签是 `org.freeinference.chat-image-digest`。
- 按发布产物部署的机器（rtx6000b 的 staging），记的是可拉取的完整地址：`ghcr.io/harvardmadsys/cloud-agent-sandbox@sha256:…`。
- `cloud-agent-sandbox` 包已于 2026-10-14 改为公开。当前版本和 19 小时前的旧版本都已验证可以匿名按 digest 拉取，所以任何机器都能取回任意历史版本的基础镜像。
- staging 一天部署好几次，每次镜像都会变。同一时刻各个组的基础镜像大多不同，所以"只让镜像相同的机器恢复"行不通，恢复时必须能按 digest 拉取旧镜像。
- 扩缩容开出来的 CloudLab 机器，由控制面把源码打包发过去，在机器上自己 build 沙箱镜像（`sandbox_host.sh` 默认 `AGENT_DEPLOY_MODE=source`）。它们记下的是本地地址，比如 `cloud-agent-sandbox@sha256:…`，别的机器拉不到。所以这些机器上的组目前不能跨机器恢复（6.9）。

**长期钥匙下发给每台机器。**

- 打开自动快照、并且填了 access key 时，控制面通过心跳把同一把长期钥匙发给每台机器。
- 按 `docs/developer/operations.md` 的要求，这把钥匙对整个 `cloud-agent/sandbox/*` 前缀都有 `s3:GetObject` 和 `s3:ListBucket` 权限。
- 所以一台机器拿到的是所有机器、所有用户归档的读权限。第一版恢复复用这把钥匙，不新增权限（6.8）。

## 二 核心决定

**改变的原则：停下的沙箱，正本在机器外面；机器上的容器只是缓存。**

1. 沙箱组每次停在一个可以证明一致的边界上，就存一个**检查点**：容器相对基础镜像的全部改动。控制面数据库记一张回执。
   - 第一版的边界是正常停止，以后可以扩展到每轮结束。
   - 回执写明：存在哪里、校验码、对应哪个 generation 和哪一次启动、每个成员的 `last_settled_job_id`。
2. 有有效检查点的沙箱组，可以在任何一台兼容的机器上恢复。原来的机器还在、缓存也还在时，用原来的机器，因为最快。
3. 换机器是一次有 fence 的操作：递增 `generation`，改绑 `host`。旧机器就算重新上线，也不能再运行或上传这个组。

**不变的原则：**

- 失败必须显式（架构文档 §2 决定 5）。恢复后仍然要用原生会话 resume，并验证恢复边界覆盖了检查点记录的 `last_settled_job_id`。验证不通过就标 `lost`。绝不重放聊天记录，也不偷偷换成空白会话。
- 任何时刻，一个沙箱组只能有一份活的副本。
- 沙箱里的内容不可信，平台凭证不进沙箱。

## 三 方案比较

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| 整机搬家（现有轮换） | 暂时保留，最终退役 | 快（演练停机 161 秒），但旧机器必须活着；只能整台搬；和扩缩容冲突 |
| 只打包三个目录（现有自动快照） | 否决 | 装在 `/usr/local/rustup` 等处的工具链和依赖会丢，恢复后 agent 可能直接出错 |
| 每次导出整个容器文件系统（删除前备份） | 否决 | 每份都带着整个镜像（约 4 GB），太大 |
| **只存容器相对镜像的改动，存到 S3（已采用）** | 已实现保存 | 内容完整，体积只有改动的部分；删除、属主、软链接都能正确保留（第九节） |
| 同样只存改动，但存到 OCI 镜像仓库 | 暂不采用，以后可升级 | 要多跑一个服务、处理 GC；S3 方案已经够快，见第九节 |
| 共享网络存储挂载 `/var/lib/docker` | 否决 | 跨站点不可行，CloudLab 的持久存储只能在一个站点内用，也会拖慢 Kata |
| 运行中的进程直接迁移（CRIU） | 否决 | Kata 下不现实 |
| 按聊天记录重放 | 禁止 | 违反架构原则 |

## 四 检查点：已实现的部分

- **抓取**：停止并完成 final 归档后，对容器执行 `docker commit --pause=false`。检查点失败不影响停止，只记 `sandbox_checkpoint_failed`。
- **导出**：Sandbox Manager 以只读方式挂载 containerd 的内容存储（`AGENT_CONTAINERD_CONTENT_DIR`），只写出这次 commit 的 manifest、config 和新增的层，格式和 `docker image save` 一样。
  - 每个字节都核对 digest。
  - 挂载缺失时退回 `docker image save`。
- **自包含**：归档包含基础镜像之外的**所有**层。从检查点恢复出的容器再被 commit 时，上一次检查点的层也算"新增"，所以每份检查点只依赖原始基础镜像，不依赖之前的检查点。代价是层数和体积会随恢复次数增长，以后再合并（第七节）。
- **大小上限**：和自动快照共用上限。超过上限的组没有检查点，不能迁移。
- **回执**：
  - 本机保存最新一张，在 `AGENT_SANDBOX_ARCHIVE_STATE_DIR/checkpoints` 下；
  - 每次心跳重复上报；
  - 控制面按 id 去重后写入 `agent_sandbox_checkpoints`。

## 五 数据模型

### 5.1 已有：`agent_sandbox_checkpoints`（迁移 `0068`）

| 字段 | 说明 |
| --- | --- |
| `id`, `sandbox_id`, `generation`, `host`, `container_id` | 哪个组、哪一代、哪台机器、哪个容器 |
| `base_image` | 基础镜像地址 |
| `object_key`, `object_version_id`, `sha256`, `size_bytes` | 存储位置和校验信息 |
| `new_layer_bytes`, `layer_count`, `members`, `durations_ms`, `format_version` | 大小、成员信息、耗时、格式版本 |
| `state` | `reported` / `verified` / `superseded` / `deleted` |

### 5.2 第一版新增

- `agent_sandboxes.state` 新增两个值：
  - `cold`：只有检查点，没有可用的本地容器；
  - `restoring`：某台机器已经领取，正在恢复。
- `agent_sandboxes.start_seq`：组的启动计数（6.2）。
- `agent_sandboxes.restore_checkpoint_id`：
  - 组停着时，是能覆盖当前状态的那个检查点，没有就为空；
  - `cold`/`restoring` 时，是要恢复的那个检查点；
  - 其他状态为空。
- `agent_sandboxes.restore_attempts`：领取恢复的次数，恢复开始前就结束（交还、失败或租约过期）的领取不算（6.6）。
- `agent_sandbox_checkpoints.start_seq`：回执对应的启动计数。
- 恢复成功后，回执的 `state` 写成 `verified`，表示真的恢复过。
- `host` 保持非空，含义变成"最近一次所在的机器"。

## 六 恢复第一版：实施方案

### 6.1 范围

**做：** 一台机器被吊销凭证之后，它上面**停着、并且有有效检查点**的对话组，在另一台机器上收到下一条消息时自动恢复。

吊销凭证有两条路：

- 管理员"移除机器"，用于机器确认死了，或者管理员决定不要了；
- 扩缩容释放机器。

两条路共用 `revoke_host_credentials`，第一版在这里处理。

**不做，留到以后（第七节）：**

- 计划内的提前搬走；
- 自动判定机器死亡；
- 正在运行的那一轮的回退；
- 闲置淘汰；
- 按沙箱发临时钥匙；
- 层合并。

### 6.2 检查点"覆盖当前状态"的判定

**难点：** 启动容器的不只是回合。文件读写、终端、Git、环境准备这些工作区请求由控制面直接转给 Manager，Manager 会自己 `docker start`，数据库里不留记录。所以控制面不能只看"组是不是 `stopped`"。

**做法：用启动计数把回执和"哪一次运行"绑在一起。**

1. 控制面在任何可能启动容器的请求转发之前，同一事务里把 `start_seq + 1`，并清空 `restore_checkpoint_id`。这些请求包括：
   - 回合的 reservation；
   - 工作区和环境请求（`_sandbox_manager_for_job` 以及环境 API）；
   - Fork；
   - 快照的捕获和导入。
2. 每个请求带上**它自己这次递增后**的计数，也就是递增语句 `RETURNING start_seq` 返回的值，而且计数跟着**真正执行的那个请求**走：回合、Fork、快照和导入写在请求体里，文件、Git、终端、环境准备这些工作区请求放在请求头 `X-Agent-Start-Seq` 里。有两种取值是错的：
   - **递增前读到的值。** Manager 记住的仍是上一次，这次运行之后的检查点永远不覆盖。2026-10-17 staging 验收就是这样失败的：网页每轮结束后会自动读取 Git 状态，这个请求带着递增前读出的对话信息，结果所有组都搬不走，机器到期时全部丢失。
   - **发送时再读的当前值。** 它可能是另一个还在路上的请求递增出来的。检查点会在那次启动之前就被当成覆盖，之后那次启动的改动在恢复时会丢失。

   重放的请求（比如重试同一个 Fork）不知道当初递增出的值，就不带计数。这样只会让检查点不覆盖，不会出错。
3. Manager 给每次运行（从启动到停止）记一个**运行计数**：这次运行里真正被接纳的请求中，最大的那个计数。只登记、还没执行的请求不算。原先的做法是把登记过的计数取最大值，再由任何一次启动拿去用，2026-10-19 的复查用两个请求复现了问题：A 带 1、B 带 2，两个都登记了，但只有 A 执行了；停止时检查点写的是 2，等于数据库，被当成覆盖，而 B 之后才到，又打开旧容器改了文件。
   - 容器停着时，请求先启动它，这次新运行的计数就是这个请求的计数。
   - 容器在运行时，请求加入这次运行，运行计数取两者中较大的。
   - 有请求没带计数（旧版控制面），这次运行就标成"无计数"，它的检查点不覆盖。
4. 一次运行停下以后，它的运行计数就**封存**了：之后到达的请求，如果计数不大于封存值，又要重新启动这个容器，Manager 直接拒绝（`StaleStartFence`，HTTP 409），控制面重新递增计数后再试。因为检查点写着这个计数，可能已经是这个组搬家要用的版本。加入正在运行的容器不受影响，那次运行的检查点会包含它的改动。

   Manager 重启后，封存值从本机磁盘上这个容器最后一张检查点回执里读回。重启时容器如果正在运行，这次运行的计数先不确定，之后带计数的请求加入时照常记录：重启前执行过的请求，计数都比它小。
5. 停止时捕获的检查点，回执带上这次运行的计数。

   这样，一张写着 N 的回执说明：计数不超过 N 的请求，要么已经执行、改动都在检查点里，要么以后会被拒绝。
6. 控制面**第一次**收到这张回执时，只有同时满足以下三条，才把它写进 `restore_checkpoint_id`：
   - 回执的计数等于组当前的计数；
   - 组是 `stopped`；
   - 回执的 host、generation、容器 ID 都是当前值。

   之后心跳重复上报同一张回执，不会再写一次。所以一旦被第 1 步清空，就不会被旧回执重新填上。
7. 兜底：心跳观察到容器在运行时，也清空 `restore_checkpoint_id`。

**两种出错的后果不一样：**

- **递增了计数，却没把新计数告诉 Manager：** 回执计数偏小，结果是"不覆盖"。不会拿旧检查点去恢复，但这个组搬不走，机器到期时就会丢。停着的组不会再捕获检查点，所以它会一直不覆盖。
- **启动路径漏了递增：** 停止时捕获的检查点本身仍是最新的。危险在于检查点之后又被这条路径启动：旧检查点仍被当成覆盖，恢复时会丢掉这次启动的改动。第 7 步只在心跳正好看到容器在运行时才兜得住。

所以每条可能启动容器的路径都必须递增，并且带上递增后的值。

**此外还要求：**

- 回执里每个有原生会话的成员，`last_settled_job_id` 都等于数据库当前值；
- 组没有进行中的 Fork，没有删除流程；
- 回执的 `base_image` 是带仓库域名和 digest 的完整地址，别的机器能拉取。

**控制面不再另外 `HEAD` 核对对象。** 归档策略不填 access key 时，控制面根本没有这个桶的凭证。回执只在上传成功后才产生；恢复方下载时会按回执核对大小和 SHA-256，不一致就恢复失败（6.6）。被攻破的机器能伪造的回执只涉及它自己的组，它本来就能破坏这些组。

### 6.3 吊销凭证时转成 `cold`

在 `revoke_host_credentials` 的同一个事务里，对这台机器上的组：

- **停着、`restore_checkpoint_id` 不为空、满足 6.2：** 改成 `cold`，`restore_attempts = 0`。排队的消息随后会被别的机器领走。
- **正在运行或启动中：** 沿用现有规则。租约过期，结果不确定的那一轮标 `LOST`。
- **停着但没有有效检查点：** 保持原状，和现在一样等同名机器重新注册；admin 沙箱页面会显示它的状态。第一版不自动标 `lost`，因为机器可能只是暂时下线。

**吊销时正在写入的心跳（2026-10-16 修订）。** 吊销之前已经通过认证的一次心跳，可能在吊销提交之后才写入检查点回执。这样的组停着、被检查点覆盖，却绑在已吊销的机器上，吊销时的转换已经错过了它。每一轮回收（`finish_host_removals`）都会对已吊销机器上的这类组补做一次 `cold` 转换（`release_late_covered_sandboxes`）。吊销之后机器再也拿不到新的覆盖，所以这一步只会转移吊销本来就会转移的组。

**cold 组不阻止"忘记"原机器（2026-10-16 修订）。** 原来 `forget_runner_host` 和删除服务器记录（`remove_allocation`）只要还有未删除的组写着这台机器，就返回 `retained_groups_present`，其中也包括 `cold` 组。可 `cold` 组已经不需要这台机器了，任何能恢复的机器都可以领取它。现在两处都不再算 `cold` 组：

- `host` 不清空：字段非空，含义仍是"最近一次所在的机器"，领取时改成领取方。
- 没有外键把组或检查点的 `host` 连到主机表，删掉主机记录不影响它们。
- 领取 `cold` 组、下发恢复信息、确认恢复出的容器，都不读组或检查点的 `host`。
- 其他未删除的组（停着的、运行中的、`restoring` 的）仍然阻止忘记。

### 6.4 领取与改绑

- 领取条件增加一支：组是 `cold`；或者组是 `restoring`，但上一次领取已经没有活的 attempt。另外要求：
  - 领取方在这次领取的声明里有 `sandbox-restore-v1`；
  - 执行配置兼容；
  - `restore_attempts` 小于上限（4，2026-10-16 起；原来是 3）；
  - 上一次恢复失败后已经等够了 6.6 规定的间隔。

  不再要求 `s.host` 等于领取方。
- 领取在同一个事务里完成：
  - 状态改为 `restoring`；
  - `host` 改成领取方；
  - `generation + 1`；
  - 清空 `container_id`；
  - `restore_attempts + 1`。
- runner 拿到的组信息带上 `restore`：检查点 id、对象位置、版本、SHA-256、大小、基础镜像。reservation 保持 `restoring` 不变，也不清空 `restore_checkpoint_id`。
- `restoring` 期间组内其他对话不能被领取，沿用现有的单活跃规则。
- 工作区请求遇到 `cold`/`restoring` 的组，直接返回"正在迁移，发一条消息即可恢复"，**不转发给 Manager**。原因：转发前会注册组，`container_id` 为空时 Manager 会走"新建组"的路，建出一个空容器。
- 快照发布后的基础提交导入（2026-10-16 修订）：组是 `cold`/`restoring` 时不下发。已经发出去的导入，只对它发出时的 `generation` 和容器生效：`complete_snapshot_base_import` 要求组当前的 `generation` 和 `container_id` 与导入请求里的一致。旧机器在恢复确认之后才回复的成功，不会把新容器记成已导入；导入随后重新发给恢复出的容器。这两个值本来就在导入请求里（`generation`、`expected_container_id`），协议不变。

### 6.5 Manager 恢复

`register_manifest` 原来的逻辑是：有 `container_id` 就接管现有容器，没有就新建。现在增加第三条路：请求带了 `restore` 就恢复。

另加一条保护：`generation ≥ 2` 的组没有 `restore` 时，拒绝新建。今天所有组的 generation 都是 1，只有改绑会让它变大。

恢复步骤：

1. **基础镜像：** 本机没有时，按回执里的地址和 digest `docker pull`，有超时。
2. **下载：** 用现有的归档凭证，按 `object_key` 和 `version_id` 把对象流式下载到 spool，同时核对大小和 SHA-256。
3. **检查归档：**
   - 结构：只允许 `index.json`、`manifest.json`、`oci-layout` 和 `blobs/sha256/*` 这几种条目；
   - 每个 blob 都和自己的 digest 一致；
   - 只描述一个镜像，`index.json` 和 `manifest.json` 里的名字必须正好是 `freeinference-checkpoint/<沙箱哈希>:<检查点 id>`；
   - 归档里没有的层，必须是基础镜像的层。

   **这一步是安全要求：** 归档是某台机器写的，被攻破的机器可以在归档里写别的镜像名，比如 Manager 镜像的名字。`docker load` 时就会在恢复它的机器上把这个名字改指到伪造的镜像。所以必须先检查，再交给 `docker load`。
4. **`docker load`：** 层由 containerd 解开，绝不在机器文件系统上解包。
5. **建容器：**
   - 用检查点镜像，按 `ChatSandboxSpec` 重新指定启动配置、网络、资源上限和磁盘配额，因为 commit 会把镜像的 Entrypoint/Cmd 换成提交时容器的配置；
   - 基础镜像标签保持原值，新增 `org.freeinference.chat-checkpoint=<检查点 id>`，generation 用新值；
   - 身份校验改为：容器创建时用的镜像名，等于基础镜像，或者等于标签所写检查点的镜像名。
   - **归档标记（2026-10-19 修订）。** 检查点是把整个容器提交下来的，Manager 自己放在 `/var/lib/freeinference-broker` 里的归档标记也在里面，记的是停止那一代的 generation 和容器 ID。新容器第一次启动前核对身份，把这张标记当成自己的，就会拒绝启动。staging 上的恢复全部这样失败。

     标记只会按容器自己的 generation 写，而恢复一定会让 generation 变大，所以同一个组、更早一代的标记只可能是跟着检查点来的。处理方式：读的时候当作不存在；启动时写入新容器自己的最终归档标记；初始归档标记不允许覆盖，采集前先把继承来的那张删掉。别的组的标记，或者同一代但容器或部署不对的标记，仍然拒绝。

     **不比较标记里的部署 namespace（2026-10-19 修订）。**每台机器的 namespace 是它自己的 Compose 项目名，各不相同，而检查点一定是在另一台机器上存的。第一版修复要求"同一个部署"，所以真实跨机器恢复时依然会拒绝；真实 Docker 测试当时只用了一个 namespace，没有测出来。同一台机器上别的部署的容器，在读标记之前就会被容器上的 namespace 标签挡掉。
   - **检查点镜像随容器删除（2026-10-17 修订）。** 这个镜像只有这台机器上这个组的容器用。原来容器删掉以后镜像一直留着，每个迁移过来、后来被删除的组都在机器上留下自己的全部改动，直到 Docker 数据盘写满。现在删除或丢弃这个组时（`remove_stopped_archived`），以及组再迁回这台机器、替换掉旧 generation 的容器时（`remove_superseded`），镜像跟着容器一起删掉；要恢复的正是旧容器那个检查点时保留，这次恢复直接用它，不必再下载，但这次恢复失败时照样删掉（6.6）。删除失败只记 `sandbox_checkpoint_image_remove_failed`，不影响删除本身。
6. **启动：** 走现有的启动、原生 resume 和恢复边界验证。通过后组变成 `running`，成员的 `context_status = restored`，回执写 `verified`。

### 6.6 失败与回退

- 第 6 步之前的任何失败（拉镜像、下载、校验、load、建容器）：
  - Manager 删掉建了一半的容器和加载的镜像，返回"恢复失败"。这个错误和"容器丢失"（410）区分开，不会把成员标 `lost`。
  - **原来两样都没删（2026-10-17 修订）。** 容器建好后检查不通过时（比如检查点镜像声明了 volume），容器连同它的匿名卷留在机器上；失败路径只删旧 generation 的容器，还特意留下这个检查点的镜像。组下次可能在别的机器上恢复，这两样就永远留在这台机器上。现在 `create` 删掉自己建出来、但没通过检查的容器，带上它的匿名卷；按 `docker create` 打印的 id 删，所以删不到别人的容器。恢复失败时再删这个检查点的镜像，不加 force，还有容器在用的镜像 Docker 不会删。同一台机器上的重试因此要重新下载一次：失败后任何机器都可以领取，这台机器也无从得知组已经去了别处，镜像留下来就再没有删除的时机。
  - runner 走现有的放弃流程，把组改回 `cold`，消息回到队列。
- **失败之间要等（2026-10-16 修订）。** 原来两次领取之间只隔着放回队列时的约 30 秒延迟，镜像仓库或 S3 中断一两分钟，3 次机会就全部用完，对话永久丢失。现在第 1、2、3 次恢复失败后，组分别要等 30 秒、5 分钟、30 分钟才能再被领取（`RESTORE_RETRY_DELAYS_S`），上限相应改成 4 次，几次尝试一共跨过 35 分钟以上。
  - 等待从失败的时刻算起，记在组的 `last_activity_at` 上：放弃、放回队列、回合结束、租约过期，每一条把失败的恢复放回 `cold` 的路径都会写它。恢复开始前就结束的领取不算失败，不写（见下一条）。
  - 领取的查询和领取时对组加锁后的复查都检查这个间隔，所以同一个组的多个对话也不能绕过它。
  - 检查点真的坏了时，组仍然会标 `lost`，只是晚 35 分钟左右。
- **恢复开始前交还的领取不算失败（2026-10-16 修订）。** 领取时 `restore_attempts` 先加 1。有的领取在机器预留这个组之前就交还了：控制面签发不了这一轮的凭证，或者机器启动不了这一轮。这时恢复还没开始，检查点也没人读过，所以组回到 `cold` 时退回这 1 次，也不改 `last_activity_at`，下一次领取只等上一次真正失败要求的间隔。原来每次交还都算一次失败，网关短暂出错时交还 4 次，对话就永久丢失了。机器已经预留了组之后才交还，或者交还原因是 `sandbox_restore_failed`，仍然算一次失败。
  - **不只是交还（2026-10-16 修订）。** attempt 在机器预留组之前结束，还有三种方式：控制面在交接时直接让这一轮失败（主人不能再用 Agent、网关不再授权这一轮的模型、仓库不再允许、团队环境被收回）；机器在预留之前就让这一轮失败；机器领取之后就死了，租约过期。这些同样没读过检查点，原来却都算一次失败，第 4 次就把对话永久标 `lost`。现在回合结束（`transition`）和租约过期（`reap_expired`）按同一条规则处理：机器没有预留组，就退回这 1 次，不改 `last_activity_at`；预留了才算一次失败。
- 第 4 次恢复仍未成功：组和成员标 `lost`，并记录原因。现有的清理会让排队的消息明确失败，不会永远排着。
  - **同组其他对话的消息（2026-10-17 修订）。** 用完次数的那次交还、回合结束或租约过期，只让它自己那个对话排队的消息失败。同组的 Fork 对话如果也有消息在排队，而排在它前面的那一轮没有成功（比如主人停止了它），这条消息永远领不到，原来也没有任何清理会让它失败。现在每一轮回收都会扫一遍：对话自己的上下文丢了、或者它所在的组是 `lost`，排队的消息就失败，不管前一轮是什么结果。
- runner 在恢复中途死掉：attempt 租约过期后，回收把组放回 `cold`，算一次失败，之后可以按 6.4 被重新领取，`generation` 再加 1。死在预留组之前的不算失败（见上）。
- 原生 resume 验证不通过：按现有规则标 `lost`。
- S3 里的检查点全程不删、不改。

### 6.7 旧机器回来

- 凭证已经吊销，旧机器无法心跳、领取或上报回执。
- 如果用同名重新注册，Manager 会从 Docker 标签重建本地的组。旧机器的观察和回执写的 generation 比数据库低，host 也可能已经变了，现有的 `host` 加 `generation` 校验会直接拒绝。它也领不到这些组，因为领取要求 `host` 一致，或者状态是 `cold`/`restoring`。
- 删除过期副本：第一版由管理员用现有的"丢弃删除"操作，以后自动。

### 6.8 安全

- 第一版复用每台机器已经拿到的长期钥匙，它本来就能读这个前缀。所以恢复不扩大任何机器的权限，也不比现在差。按沙箱发临时钥匙是单独的后续工作（第七节）。
- 检查点内容不可信：
  - 只有通过 6.5 第 3 步的检查后才交给 `docker load`；
  - 下载内容必须和数据库里回执的 SHA-256 一致。
- 被攻破的机器最多能伪造它自己当前运行的沙箱的检查点。它本来就能改这些沙箱，所以没有新增风险。
- 两份活副本：最后一道防线是 fence。改绑要求在事务里递增 generation；旧机器的凭证已吊销；对账拒绝过期 generation。

### 6.9 扩缩容机器改为拉取已发布的镜像

- 在扩缩容机器上建的组，记下的是本地镜像地址，不满足 6.2 的"可拉取"条件，所以不会被转成 `cold`。它们的行为和现在一样，不会更差。
- 同一个 PR 里，让扩缩容机器按部署的提交，从 ghcr 拉取已经发布的沙箱镜像，不再本地 build。改完后，这些机器上新建的组也能跨机器恢复。
- 扩缩容机器只要声明了 `sandbox-restore-v1`，就能恢复别的机器的组，因为包是公开的。

### 6.10 实施与验收

整个第一版放在一个 PR 里：本文档、迁移、控制面、Manager、runner、扩缩容部署。

额外检查：`make ci-database`、`make ci-frontend`（admin 页面显示 `cold`/`restoring`）、`make docs`，以及在 containerd dind 里跑一遍"捕获、在另一个 daemon 上恢复"的端到端测试。

上线兼容性：

- 没有声明 `sandbox-restore-v1` 的机器不会领取 `cold` 组；
- 旧 Manager 的回执不带计数，所以永远"不覆盖"，不会被转成 `cold`。

**staging 验收**（rtx6000b，加一台装了新 Manager 的 CloudLab 机器）：

1. 在一台机器上建 Claude Code 会话、它的 Fork 和一个 Codex 会话，写入文件，在 `/usr/local/rustup` 下装点东西，然后停止。
2. 移除这台机器，再给三个会话发消息：都在另一台机器上恢复，口令、文件和工具都在，`context_status = restored`。
3. 用同名重新注册旧机器：确认已迁走的组不会被启动，回执也不会被接受。
4. 记录恢复各步的耗时：拉镜像、下载、load、启动、resume。

## 七 以后

按价值排序，每一项都要单独设计：

1. **计划内腾空**（到期、缩容、管理员手动）：提前在目标机器上恢复好并保持停止状态，用户的下一条消息只是普通启动，完全无感。有了它，扩缩容的缩容和 CloudLab 到期都不再需要整机搬家。
2. **按沙箱发临时钥匙**：STS 只授权 `sandboxes/<沙箱哈希>/`，长期钥匙不离开控制面。需要有 AWS 权限的人加 `sts:*` 权限，可以提前去申请。
3. **自动判定机器死亡**：心跳超时，并且云平台确认机器已经不存在。已部分实现：云平台确认机器已终止（`terminated`）后，有检查点覆盖的停止组转成 `cold`（#708）；其余的组在主机静默 10 分钟、且没有进行中的回合、领取或 Fork 时标为 `lost`，排队的消息明确失败（2026-10-16，staging 两台机器到期后对话一直挂在已消失的机器上）。只有心跳超时、云平台没有确认的情况仍不处理。
4. **腾空时补捕获检查点**：停着、但检查点不覆盖的组（检查点失败、Manager 重启后没收到过计数、或以后再有计数错位），在腾空时由控制面带上当前计数，请 Manager 对停止的容器重新 `docker commit` 一次，不启动容器。这样计数出错只会让搬家慢一点，不会让对话随机器到期丢失。需要 Manager 新增接口和能力声明。
5. **每轮结束存检查点**，以及**跑到一半死了时回到上一轮**（新的产品状态 `rewound`，加"重试这一轮"按钮）。
6. **层合并、保留和删除规则**：每个沙箱保留最近 K 个检查点；删除对话或账号时一并删除；桶上配置未完成分块上传的清理规则。
7. **闲置淘汰**：不计划。机器的生命周期大概率比淘汰周期短；正本已经在 S3，机器活着时原地启动就够了。只有出现磁盘压力时，再考虑按"最久没用"清掉本地缓存。

## 十 风险

- **大沙箱恢复很慢**：突发故障时用户要等较长时间。以后靠计划内提前恢复缓解。
- **检查点在停止时失败**：这个组不能迁移。机器随后死掉的话，它就停在原机器上，等机器回来。
- **基础镜像被删**：ghcr 上的旧版本必须一直保留，否则依赖它的检查点无法恢复。镜像清理规则要和检查点保留规则联动。
- **层数增长**：每恢复一次多一层，overlay 有层数上限，要在接近上限前做合并。
- **合规**：用户代码和对话存放在 CloudLab 之外。开放生产前需要确认数据存放的要求。

## 十一 不做的事

- 不迁移运行中的进程（CRIU）。
- 不按聊天记录重放来"恢复"会话。
- 第一版不新增任何机器侧的云存储权限。
