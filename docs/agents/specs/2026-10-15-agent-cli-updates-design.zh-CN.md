# Agent CLI 一键更新设计

日期：2026-10-15。状态：与同一 PR 中的实现一致。

设计核对基线：远端 `dev`，提交 `95be1af9`。

目标：管理员在 Admin 的 Settings 页面点一下，就能把 Claude Code、Codex、OpenCode 或 pi 更新到 npm 上的最新版本，或者换成 npm 上的任意一个正式版本（包括更老的），不用改代码、重建镜像或重新部署。

## 一 原有行为与问题

agent CLI 的版本是打包在沙箱镜像里的。默认版本同时写在两处：`deploy/sandbox/Dockerfile.agent-sandbox` 和 `cloud_agent_shared/shared_protocol.py`。想用其他版本，有两条路：

- 改默认版本：改代码、重建镜像、发布，并跑一遍兼容性测试。
- 加额外版本：在部署主机上设置 `*_EXTRA_VERSIONS`，重新构建镜像，再在 Admin 里选用。

两条路都要重建镜像，所以版本从 7 月起就没动过。设计时（2026-10-14）的差距：

| Agent | 镜像里的版本 | npm 最新 | 落后的正式版本数 |
| --- | --- | --- | --- |
| Claude Code | 2.1.220（7/24） | 2.1.299 | 67 |
| Codex | 0.145.0（7/21） | 0.162.1 | 33 |
| Kilo | 7.4.17（7/29） | 7.8.8 | 38 |
| OpenCode | 1.18.9（7/28） | 1.19.0 | 27 |
| pi | 0.73.1 | 0.73.1 | 0 |

## 二 已确定的产品决定

| 问题 | 决定 |
| --- | --- |
| 怎么更新 | Admin 页面一个按钮。点了以后，每台主机在运行时自己下载这个版本，不重建镜像。Murphy 于 2026-10-14 选定，并接受由此带来的变化：生产环境运行的 CLI 版本不再完全由发布的镜像决定。 |
| 支持哪些 agent | Claude Code、Codex、OpenCode、pi。Kilo 不支持：我们运行的是带隔离补丁的源码构建，npm 上的官方包没有这个补丁。 |
| 界面上的状态 | 正常只有两个："下载中"（显示一个小恐龙进度条）和"已完成更新"。下载或自测失败时，显示原因和"重试"按钮。 |
| 什么时候切换 | 所有在线主机都下载好、并且自测通过之后，新对话才开始用新版本。已有对话一直用它开始时的版本。 |
| 回退 | 一键回到更新前新对话所用的版本。 |
| 任意版本 | 版本下拉框列出 npm 上的所有正式版本，可以升级也可以降级。Murphy 于 2026-10-15 决定：预发布版（alpha、beta 等）不列出。 |
| 交付方式 | 设计、实现和测试放在同一个 PR 里。 |

## 三 用户可见行为

Settings → Agent versions 里，每个可以更新的 agent 下面会显示：

- **有新版本时**：显示"Update to 2.1.300"按钮。
- **点了之后**：显示小恐龙进度条，进度是所有在线主机进度的平均值。只有新对话真正切换过去，进度条才会走到 100%。
- **完成后**：显示"Updated to 2.1.300"，旁边有"Roll back to …"按钮。
- **失败时**：显示是哪台主机失败、失败原因，以及"Try again"按钮。如果切换还没发生，新对话仍然用原来的版本，页面上也会写明这一点。
- **已经是最新时**：显示"Up to date"。
- **查不到 npm 时**：显示原因，同时不提供更新按钮。

版本下拉框分两组：**On servers** 是服务器上已经有的版本，**Download from npm** 是 npm 上其余的正式版本，新的在上面。

- **选一个每台服务器都已经有的版本**：按钮是"Save"，保存后马上生效。
- **选一个有服务器还没有的版本**：按钮变成"Download and switch"，下面写明有几台服务器要先下载并自测。点了之后和"Update"走完全一样的流程：小恐龙进度条，所有服务器都通过后新对话才切过去。所以降级到老版本，也要先通过同样的自测。
- **不列出的版本**：预发布版（版本号带 `-`，比如 `0.162.0-alpha.1`、opencode 的 `0.0.0-snapshot-…`），以及 npm 标了废弃的版本（比如 Codex 0.54.0："bad MUSL binaries on Linux"）。例外：如果 npm 的 latest 版本本身也被标了废弃，说明废弃的是整个包而不是某个版本，这时照常列出所有版本，并在页面上显示 npm 的说明。pi 目前就是这样：npm 上旧包 `@mariozechner/pi-coding-agent` 的每个版本都写着"please use @earendil-works/pi-coding-agent instead going forward"。
- **查不到 npm 的版本列表时**：下拉框仍然列出服务器上已有的版本，并显示原因。
- **Kilo 不变**：只能选镜像里自带的版本。

版本列表来自 npm 的精简包文档（`application/vnd.npm.install-v1+json`）。这份文档很大，opencode 的约 15 MB，所以版本列表用单独的接口 `GET /admin/agent/runtime-upgrades/{runtime}/versions` 读取，不放在页面每隔几秒的轮询里。控制面每个包每小时最多读一次，同一时间只读一次，读失败的结果只缓存 1 分钟；页面每次打开这个标签时读一次。

在下拉框里手动选一个版本，会取代正在进行或已经完成的更新，以手动选择为准。手动选的版本（包括回退）同样会下发给每台主机：后加入的主机，或者丢了这份下载的主机，也会去下载它。如果有主机下载失败，页面会显示"Some servers could not download …"和"Try again"按钮；没有失败时，页面不显示额外信息。

## 四 一次更新怎么完成

```
管理员点 Update ─► 控制面 POST /admin/agent/runtime-upgrades
                   校验版本在 npm 上存在，记录目标：
                   {version, before=当前时间, nonce, previous_version,
                    previous_download=新对话现在所用版本的下载记录}
                          │ 每次心跳的回复里都带上要保留的版本（每个 runtime 最多两个）
                          ▼
每台主机的 runner ─► RuntimeDownloads 一次处理一个版本
   1 下载    npm install --ignore-scripts --before <before>
             联网，但只运行 npm 自己
   2 装脚本  npm rebuild，断网；再检查 --version 是否完全一致
             把装好的目录复制到一个新的沙箱镜像容器上，只提交这一层
   3 自测    断网的容器里用生产驱动跑一轮对话，对接回环地址上的假模型
   4 保留    通过后才打上正式标签，主机从这里查找已下载的版本
                          │ 每次心跳上报 {state, progress, error}
                          │ version_stamp 的可用版本里会包含这个版本
                          ▼
控制面 ─► 每次心跳后检查：如果每台在线、已注册的主机都提供这个版本，
          就把新对话切换到这个版本，并记录 activated_at
                          │
                          ▼
新对话第一次启动成员时 ─► 把这个版本的文件复制进对话容器自己的写层：
                         /opt/runtimes/<runtime>/<version>
                         然后照旧把这个目录放到 PATH 最前面
```

几处具体约定：

- **下载的版本存在哪里。** 存成主机本地的 Docker 镜像：`<namespace>-agent-runtime:<runtime>_<version>_<基础镜像ID前12位>`。runner、每个对话进程和沙箱管理进程是不同的进程，沙箱管理进程还在另一个容器里，它们唯一共享的是 Docker daemon。所以不需要新加任何主机目录挂载，也不需要进程之间互相询问（`runtime_images.py`）。
- **为什么复制进对话、而不是挂载进去。** 对话的状态必须全部在容器写层里，`_verify_mounts` 会拒绝任何挂载。复制进去之后，对话归档、恢复或迁移到别的主机时，CLI 会跟着一起走；主机上的下载镜像删了，也不影响已有对话（`runtime_install.py`）。
- **复制前的检查。** 只有整棵目录都归 root 所有、并且只有 root 能写时才会启用，所以成员改不了别的成员要运行的 CLI。整棵目录写完后才写标记文件，复制到一半中断的目录不会被当成完整的。
- **新镜像发布之后。** 新的沙箱镜像发布后，主机会把每个目标重新下载、重新自测一遍，因为之前的自测是在旧镜像的 wrapper 和 Node 上做的。重新下载期间，旧镜像上的那份仍然可用，不会出现退回默认版本的空窗期。新的下载通过后，删除旧镜像上的那份。如果重新自测失败，页面显示"更新失败"，管理员可以回退。
- **`--before` 的作用。** 它把 npm 的依赖解析固定在管理员点击的那一刻。pi 的依赖写的是版本范围，有了这个参数，一周后才下载的主机也会装出一模一样的依赖树。
- **每台主机要保留哪些版本。** 每个 runtime 最多两个：更新要切换到的版本；以及在切换完成之前，新对话现在所用的那个已下载版本。第二个是必须的：更新还在下载、或者已经失败时新加入的主机，也要能运行其他主机正在运行的版本，否则它会悄悄用自己的默认版本开新对话。切换完成后只下发新版本；主机上已有的旧版本不会删除，所以回退在这些主机上是即时的。
- **重试。** 对同一个版本再点一次（Try again）就是重试，只换一个新的 nonce。旧的失败只对应旧 nonce，所以不会再被计入。`before`、"回退到哪个版本"、是否已经切换，都保持不变：已经装好的主机保留的是当时解析出的依赖树，重试的主机必须解析出同一棵；已完成的更新在新主机上重试，也不会变成"回退到它自己"。
- **回退。** 回退就是手动选择更新前的版本。这个版本会继续下发给每台主机，并沿用它第一次下载时的 `before`，所以之后才下载它的主机装出的依赖树和其他主机一致。

## 五 安全边界

- **只有下载这一步联网。** 这一步只运行 npm 本身（它属于已审核的镜像），并且关闭所有包脚本。npm 会用 registry 提供的完整性哈希校验每个包。网络默认是 Docker 的 `bridge`，可以用 `AGENT_RUNTIME_DOWNLOAD_NETWORK` 换成别的网络。
- **包自己的安装脚本在断网环境里运行。** 所有安装容器都去掉了全部 Linux 权限（capability），设置 `no-new-privileges`，并限制进程数量。对比一下：沙箱镜像本身的 `docker build` 是以 root、联网运行这些脚本的，所以这里比镜像构建更严格。
- **自测在断网容器里进行，以成员身份运行。** 假模型只监听容器内部的 127.0.0.1。自测和安装都用 runc，没有用 Kata，信任模型和镜像构建一样，因为运行的是厂商发布的包，而不是用户的代码。
- **不能安装任意包。** 包名来自代码里固定的目录（`runtime_catalog.py` 里的 `npm_package`）。控制面只接受精确版本号，并且会先确认 npm 上确实有这个版本。
- **沙箱网络边界、凭据和挂载规则都没有改。** 对话容器不会多出任何挂载、网络或权限。

## 六 版本记录与协议

- 每次 attempt 照旧记录 `runtime_version`。主机上报的可用版本里包含已下载的版本，claim 时的回退规则（`resolve_runtime_version`）不变。
- 共享 sandbox 协议里固定的默认版本（`SHARED_SANDBOX_RUNTIME_PINS`）不变。新版本是通过"管理员的选择"生效的，不是通过修改默认版本，所以 `shared-sandbox-v1` 的认证不受影响。没有选择时，主机仍然运行镜像默认版本。

## 七 存储与接口

- 迁移 `0075_runtime_upgrades`：
  - `agent_runner_policy.runtime_upgrades`（JSON 对象）：每个 runtime 一条记录。`kind` 是 `update`（点 Update 发起的）或 `selection`（手动选择或回退）。
  - `agent_runner_hosts.runtime_downloads`（JSON 数组，可以为空）：每台主机对每个要保留的版本的上报。

  两列都是新增、默认为空。旧版本的控制面和主机会直接忽略它们。
- 心跳请求加 `runtime_downloads`：每个要保留的版本一条，带 `runtime`。读不懂的条目（包括 `state` 不是字符串的）直接丢掉，不会因此拒绝整个心跳。心跳回复加 `runtime_downloads`，内容是每台主机要保留的全部版本，包括已经完成的更新，这样后加入的主机也会去下载。
- `GET /admin/agent/runtime-upgrades`：返回每个 agent 当前给新对话用的版本、npm 最新版本、更新状态和进度。npm 的查询结果缓存 1 小时，查询失败只缓存 1 分钟。
- `POST /admin/agent/runtime-upgrades`：发起更新，并写入审计记录 `agent.runtime_version.upgrade`。版本可以是 npm 上任意一个已发布的精确版本，更新或更老都可以。
- `GET /admin/agent/runtime-upgrades/{runtime}/versions`：返回这个 agent 在 npm 上的正式版本（新的在前）、整个包被废弃时 npm 的说明，以及读取失败的原因。
- 回退复用 `PUT /admin/agent/runtime-versions`。它现在会用手动选择的版本取代这个 runtime 的更新；选的是可下载的 agent 时，这个版本继续下发给每台主机。选回"默认"时清除记录，因为镜像默认版本每台主机都有。
- 新增环境变量（见 `ENVIRONMENT.md`）：
  - `AGENT_RUNTIME_REGISTRY_URL`：控制面和主机都会读，默认是公共 npm registry。
  - `AGENT_RUNTIME_DOWNLOAD_NETWORK`：只有主机读，默认是 `bridge`。

## 八 代价与限制

- **每个新对话都要复制一份 CLI 到自己的写层，并计入对话的磁盘配额。** 实测解压后的大小：

  | Agent | 大小 |
  | --- | --- |
  | Claude Code | 约 253 MB |
  | Codex | 约 390 MB |
  | pi | 约 206 MB |
  | OpenCode | 约 177 MB |

  镜像里自带的版本没有这项开销。
- **每个已下载的版本在主机上占一层镜像，大小同上。** 新镜像发布后旧的那份会被删除，但不再被任何目标引用的版本不会自动清理，留作后续工作。
- **自测只能证明一件事：一轮对话的输出，生产驱动都能读懂，并且模型的回答出现在对话里。** 它覆盖不了 `drivers.py` 里那些照着固定版本具体行为写的处理，比如中途插话、后台子 agent、权限提示等。所以建议先在 staging 更新，确认没问题再更新生产，有问题就回退。
- **要求所有在线主机都升级到包含此功能的 runner，切换才能完成。**
- **控制面必须能访问 npm registry**（或 `AGENT_RUNTIME_REGISTRY_URL` 指定的 registry），否则页面上会提示无法检查更新。

## 九 验证

- **单元测试：**
  - 版本匹配规则与 `install-runtimes.sh` 逐条对照；上报和目标的格式校验；进度汇总（平均值、失败优先、按 nonce 区分请求、已完成的更新在重新自测期间保持已完成）；npm 查询和缓存；版本列表只留正式版、按数字从新到旧排、去掉废弃版本，整个包被废弃时照常列出并带上说明；版本列表每小时只读一次、同时只读一次、读失败很快重试（`test_runtime_upgrades.py`）。
  - 主机端用假的 Docker：联网和断网分别在哪一步、只保留自测通过的版本、失败后的重试规则、新镜像发布后重新下载、同一个 runtime 同时保留两个版本、清理遗留容器；复制进对话（`test_runtime_downloads.py`）。
  - 心跳收发（`test_host_pool_api.py`、`test_host_enrollment.py`），Admin 接口，包括版本列表接口和选更老的版本（`test_admin_runtime_upgrades_api.py`），版本上报（`test_agent_sandbox.py`）。
- **数据库测试**：所有在线主机就绪后才切换、没有主机在线时不切换、上报的存储；重试只换 nonce（`before`、回退目标、切换状态都不变）；切换前主机同时保留在用的版本；回退后这个版本继续下发并沿用原来的 `before`；手动选择会取代更新、选回默认会清除（`test_host_pool_store.py`）。
- **前端**：更新、下载中显示恐龙、完成后刷新版本菜单、失败与重试、回退、手动选择的版本下载失败、查不到 npm；下拉框分组列出 npm 版本、选服务器没有的版本走"下载并切换"、选都有的版本照常保存、整个包被废弃和读不到版本列表时的提示；恐龙进度条本身（`page.test.tsx`、`DinoProgress.test.tsx`）。
- **真实环境**（`tests/external/test_runtime_updates_live.py`，需要已构建的沙箱镜像和 npm 网络）：在本机 Docker 上，用真实的 npm 和 CLI 跑完整条流程。Claude Code 2.1.300 和 OpenCode 1.19.0 能下载、自测、出现在可用版本里，复制进容器后成员能运行但不能修改；pi 0.73.1 走"镜像里已有"的路径；没有安装的版本自测会失败。开发过程中也用同一套代码跑通了 Codex 0.162.1 和 Claude Code 2.1.299。降级也用真实流程跑通了：Claude Code 2.1.200、Codex 0.140.0、OpenCode 1.18.0，都比镜像默认版本老。版本列表接口直接对真实 npm 调用：四个 agent 第一次共约 0.8 秒，之后走缓存；每个回复不到 9 KB。
