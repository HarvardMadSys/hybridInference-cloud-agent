# 执行阶段公网访问：第一阶段设计

- 日期：2026-09-23
- 状态：已评审的实施方案，尚未实现；生产默认网络策略未变
- 替代：2026-09-22《第一阶段：Cloud Agent 受控公网访问设计》、配套实施 prompt、P0 报告及其实验 harness。它们只存在于本地分支 `codex/network/controlled-public-egress` 和 `murphy/deepseek/controlled-public-egress-phase1`，从未合入 `dev`。**不要再按旧文档的 P0–P3 路线实现，也不要合并这两个分支。**
- 相关：[沙盒安全模型](2026-09-01-agent-sandbox-security-model.zh.md)（现行安全契约）、[AGENTS.md](../../AGENTS.md) §6–§7

## 1. 目标

用户可以直接让 Agent "安装依赖、运行测试、缺什么补什么、需要时查文档，然后修复失败"。setup 和 agent 两个阶段都能用 curl、Python HTTP 客户端、pip、npm、Git over HTTPS 访问公网。

网络边界由平台统一规定，所有任务相同，用户不选择网络模式。

## 2. 固定边界

| 类别 | 规则 |
|---|---|
| 允许 | 公网 IPv4 的 TCP 80/443；指定解析器的 TCP/UDP 53；两个中继的精确地址与服务端口 |
| 拒绝 | 宿主本机；私网、链路本地（含云元数据）、CGNAT、组播等非公网 IPv4；其他沙盒组与其他环境的地址池；部署方追加的受保护网段；上述之外的所有端口；全部 IPv6 |
| 凭证 | 长期平台凭证不进沙盒；短期推理令牌和 MCP 令牌仍在沙盒内 |

三点措辞限定：

- 防火墙保证的是"公网 IPv4 TCP 80/443"，不识别端口里传的是不是 HTTP。
- 开放公网后，沙盒内的程序可以把仓库内容和沙盒里的短期令牌发出去。这是联网能力本身的代价，本设计不承诺防外发。
- "控制面的公网入口拒绝沙盒令牌"和"沙盒连不上控制面"是两个不同承诺。控制面、网关的公网地址不会因为禁止私网而被挡住；本设计只保证前者（§4）。

## 3. 配置

- 新增 egress 档 `public_web`。setup、agent 两个阶段都用它时，就是本设计的行为。
- 只有运维开关，没有用户选项：沿用 `AGENT_EGRESS_SETUP_TIER` 和 `AGENT_EGRESS_AGENT_TIER`。`trusted`（白名单代理）和 `platform_only`（只有两个中继）保留为运维档。
- 发布代码不改变默认值。staging、prod 的切换是验收通过后的单独部署动作。

## 4. 前置条件：阻止令牌被公网直接重放

开启 `public_web` 之前必须完成：

1. **MCP 工具调用只在 8001 提供。** 主 API（公网边缘把 `/api/*` 转发给它）不挂载工具中继路由；连接管理、OAuth 回调和调用审批与它共用 `/v1/agent/mcp` 前缀，仍留在主 API。所以不能在边缘直接封掉整个前缀。见 [#327](https://github.com/HarvardMadSys/hybridInference-cloud-agent/pull/327)。
2. **网关只在独立的内部监听入口接受推理令牌。** 网关的 `verify_api_key()` 收到 grant 令牌后只检查是不是推理路径，不区分请求从哪个入口进来。服务只监听 `127.0.0.1` 不够，公网反向代理可能转发到同一个端口；也不能靠调用方能伪造的请求头判断。改动在网关仓库，按 HTTP 合同进行。

目标是"阻止公网直接重放"，而不是"令牌带出沙盒就没用"。中继没有把令牌绑定到特定沙盒，另一个能访问中继的沙盒拿到令牌后仍可能使用。所以现有的任务权限、工具审批和撤销检查全部保留。

## 5. 架构

```text
沙盒 ──组网桥──┬─> 推理中继 ──SSH──> 网关内部入口
              ├─> MCP 中继 ──SSH──> 控制面 8001
              └─> 宿主（路由和 NAT）──> 公网 IPv4 TCP 80/443
                   宿主 nftables 表：同时拦截 INPUT 和 FORWARD
```

和现在相比：

- **保留**：每组一张网桥、从地址池分配 /29、两个中继的挂接方式、setup→agent 切换时 Kata guest 重启、成员进程与凭证隔离。
- **改变**：`public_web` 的组网桥不再是 `--internal`，宿主侧有网关地址，由 Docker 负责路由和 NAT。
- **新增**：宿主上一张由我们管理的 nftables 表、指定解析器的 DNS、启动自检。

## 6. 宿主规则表

由 runner host 一侧的受信组件安装，不在沙盒内。

1. **独立表，按环境隔离。** 表名包含部署命名空间，只匹配本环境的地址池。不执行全局 flush，不切换 Docker 防火墙后端，不修改 Docker 或其他服务的表。独立规则表不等于独立宿主环境，§7 的地址池要求是前提。
2. **FORWARD（经宿主转发）。** 源地址属于本环境地址池时：目的地址在受保护集合里（私网、链路本地、CGNAT、组播、其他地址池、部署方追加网段）就拒绝；TCP 80/443 放行；指定解析器的 TCP/UDP 53 放行；其余拒绝。Docker 端口映射要按 DNAT 之后的真实目的地址判断，必须实测覆盖。
3. **INPUT（访问宿主本机）。** 来自本环境地址池、发往宿主本机任何地址（包括网桥网关地址）的流量一律拒绝。解析器如果跑在宿主上，只放行它的地址和 53 端口。只管 FORWARD 挡不住宿主上的服务。
4. **桥内到中继。** 只按两个中继的实际地址和服务端口精确放行，不能为了放行它们而放开整个私网。中继在每张组网桥上的地址不同，由 runner 在把中继接入网桥时写进一个"地址+端口"集合，撤下时删除；规则本身保持固定。Linux 可能让桥内流量也经过 IP 层钩子，这一点要实测。
5. **IPv6。** 本环境网桥不启用 IPv6，并额外加一条 IPv6 全部拒绝的规则。IPv6 支持以后再做，IPv6 阻断本期必须实现并验收。
6. **回拒绝，不静默丢弃。** 被拦的连接立即报错，程序和 Agent 不必等超时。
7. **与 Docker 规则的先后。** 同一个钩子上，任何一条基础链丢弃就是最终结果；具体顺序和 Docker 自己生成的规则怎么交互，要在真实宿主上确认。

## 7. 地址池

staging 和 prod 目前默认都用 `AGENT_EGRESS_CHAT_NETWORK_POOL=10.240.0.0/16`（[docker-compose.sandbox.yml](../../deploy/host/docker-compose.sandbox.yml)）。不同的 Compose 项目名只区分资源归属，不会分配不同的地址池。

启用 `public_web` 前，每个环境必须显式配置互不重叠的地址池，规则只匹配各自的池。runner 启动时检查本环境的池和宿主上其他已知池（从带环境标签的 Docker 网络读取）不重叠，重叠就不声明 `public_web` 能力。

## 8. DNS

- 现在沙盒的 `--dns` 指向 `127.0.0.1`，故意让外部域名解析失败（[chat_sandbox.py](../../apps/backend/cloud_agent_host/chat_sandbox.py) 的 `CHAT_DNS_UPSTREAM`）。
- `public_web` 指定一个解析器。runc 容器通过 `--dns` 设置；Kata guest 访问不到 Docker 内置的 `127.0.0.11`，由受信 helper 写入 guest 的 `/etc/resolv.conf`，方式和现在写中继的 hosts 条目一样。
- 只放行这个解析器的 TCP/UDP 53，不能放行任意目的地址的 53。

## 9. 生命周期

1. **先有规则，再声明能力。** runner 启动时安装规则表并自检。表缺失或自检失败，就不声明 `public_web` 能力，不领取需要它的任务。
2. **网络就绪之后才跑代码。** 组网桥、规则表、DNS 和沙盒内自检全部通过后，才运行任何仓库代码或依赖安装脚本。
3. **自检要有对照。** 每个拒绝项都要指向一个正在监听的受控服务，并有"同一个服务从允许的路径可达"的正向对照。目标本来就不通，不能算防火墙生效。
4. **失败就断开。** 自检或启动失败时，断开或清理这个组的出口，标记失败，保留工作区。
5. **重新自检的时机。** setup→agent 切换、沙盒恢复复用、Docker 或宿主重启、规则表重装之后都要重新自检。启动时通过一次，不能证明这些路径也安全。

## 10. 回退

只改两个环境变量不够。沙盒会被保留复用，改配置既不会断开已有连接，也不会替换运行中沙盒的网桥（[chat_sandbox.py](../../apps/backend/cloud_agent_host/chat_sandbox.py) 的 `start()` 对运行中的容器直接复用）。回退步骤：

1. 停止新任务进入公网模式：runner 不再声明 `public_web` 能力。
2. 撤掉存量沙盒的公网出口：规则表对本环境地址池改为全部拒绝（中继除外），再断开或替换存量沙盒的可路由网桥。
3. 恢复配置，重启相关服务。
4. 验证恢复后的沙盒和原有连接都无法继续出网。工作区保留。

## 11. 验证

**第 3 步开头先做最小 Kata 验证**，走产品代码路径：普通网桥上的 guest 路由、DNS、两个中继可用、宿主阻断。通过后再完成核心 PR。

**第 4 步的完整验收先在独立 Kata 环境做**，通过后再到共享机器上的 staging 检查部署兼容性。挑低峰时间只能缩小影响范围，不能证明规则安全。

验收项（每个拒绝项都要有正在监听的目标和正向对照）：

| # | 场景 | 期望 |
|---|---|---|
| 1 | curl、Python 访问公网 HTTPS（开启证书校验） | 成功 |
| 2 | 公网 HTTP 80 | 成功 |
| 3 | 公网其他 TCP 端口（如 22）、UDP 443 | 立即被拒 |
| 4 | 宿主本机的监听服务（含网桥网关地址、Docker 映射端口） | 被拒 |
| 5 | 私网、实验室网段、部署方追加网段上的监听服务 | 被拒 |
| 6 | 169.254.169.254 等链路本地地址 | 被拒 |
| 7 | 另一个沙盒组内的监听服务、其他环境的地址池 | 被拒 |
| 8 | 中继的服务端口 / 中继的其他端口 | 可用 / 被拒 |
| 9 | 直连指定解析器以外的 53 端口 | 被拒 |
| 10 | 任何 IPv6 目的地址 | 被拒 |
| 11 | 在沙盒内修改路由、防火墙或 DNS 配置 | 失败，规则不变 |
| 12 | 网络就绪前运行仓库代码或安装脚本 | 不发生（由执行顺序保证并有测试） |
| 13 | 自检失败 | 出口断开，任务标记失败，工作区保留 |
| 14 | 沙盒恢复复用、setup→agent 切换、Docker 重启、宿主重启 | 重新自检，以上结果不变 |
| 15 | 按 §10 回退 | 存量沙盒和原有连接都无法出网 |
| 16 | 在主 API 上使用沙盒 MCP 令牌、在网关公网入口使用推理令牌 | 都被拒（§4） |

## 12. 实施步骤

## 13. 不做（以后再说）

- 用户可选的网络模式、按任务的域名名单、策略快照和 Fork 策略继承。
- 每组网关容器、往 Kata guest 注入路由、网络租约。
- 完整出站审计、滥用监控、IPv6 支持。

## 14. 可复用的旧实验材料

旧 harness 在 `codex/network/controlled-public-egress` 分支的 `tests/external/egress_phase1/` 下。有三样可以搬到第 3、4 步：受保护地址分类器（`address_classifier.py`）、双向持续流量探针、向规则里故意插入漏洞来检验测试的方法。其余部分（每组网关容器的拓扑、按目的 IP 的租约）不适用于本设计。
