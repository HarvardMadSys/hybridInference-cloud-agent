# CloudLab 节点自动轮换与整机迁移设计

日期：2026-10-10。状态：手动跨站点真实会话演练已通过；自动轮换与管理界面已实现，本地前后端和数据库全量检查已通过。自动流程的 staging 验收和两周无人值守验收尚未完成。

设计核对基线：远端 `dev`，提交 `ccc17e59`。本文是 [计算资源生命周期设计](2026-10-04-compute-resource-lifecycle-design.zh-CN.md) 里留到"后续"的跨机器迁移用例，只覆盖 CloudLab 节点到期这一种场景。

## 目标

Cloud Agent 的沙箱放在 CloudLab 上，稳定到能上生产。节点到期或续期被拒时，系统自动换一台新节点，把沙箱整机搬过去。用户感觉不到，会话不丢，整个过程不需要人盯着。

## 一 背景与约束

CloudLab 侧（2026-10-08 至 10-10 实测并核对文档）：

- 实验必然到期，到期后本地盘被清空重装，无法恢复。
- 短续期自动批准，长续期要 CloudLab 工作人员审批；工作人员对项目用量有疑问会联系项目负责人。
- 续期会被别的项目的预留挡住（10-08 实际发生），新建也可能失败。
- 实验状态 `failed` 并不等于没有空闲：10-09、10-10 在 FAST25-AE 下申请 CloudLab 集群的机器全部失败，涉及五种机型、两个站点，其中也包括 10-08 成功过的同一配置。Portal API 不返回失败原因。
- 从 10-09 起，API 收到 JSON 布尔值的 `bindings` 会返回 400；服务端把绑定值存成字符串。
- API 所在主机偶尔返回一张已经过期的证书，导致 TLS 握手失败。
- 已认证 API 返回的 manifest 里没有节点的 SSH 主机公钥。
- API 可以创建和更新 profile，profile 可以设为只有项目成员可见。

代码侧（`dev` 现状）：

- 沙箱的工作区和原生会话只在容器可写层里。空闲时 `docker stop`，下次使用时 `docker start`，在同一个容器里恢复。系统里没有按聊天记录重建会话的路径。
- 每个保留的沙箱固定在一个主机名上，后续回合只会派给这个主机名。
- 主机暂停领取任务或暂时离线时，用户的后续消息照常收下并排队，没有超时。
- 单个回合有 1 小时的硬上限（`AGENT_TIMEOUT_S`，默认 3600 秒，可在管理页调整）。
- 回合运行中停掉 runner 时，runner 最多等待 5 分钟；超时的回合会失败，会话被标为 LOST。
- 主机名由节点生成，代码拒绝把已有的主机名绑定到另一台节点。
- 节点上还有保留沙箱时不允许释放。
- 同名重新登记已有支持，登记时会作废这个名字原来的凭据。
- 控制面对外的 API 地址来自 `AGENT_SESSION_REDIRECT_URI`（去掉回调后缀），与 MCP 回调使用的地址相同。

## 二 方案选择：整机搬家

节点会换以后，沙箱状态只有两种保存办法：

- **跟着机器走（本方案）**：每次换节点，把整台机器的 Docker 数据直接拷到新节点。会话机制不用改，也不需要外部存储。
- **存到节点外面**：沙箱停下后导出到持久存储，下次使用时在当前节点上恢复。CloudLab 自带的持久存储只能在一个站点内使用，有配额，速度慢，可能需要审批；放到 CloudLab 外面，恢复时要跨公网拉取数据，还有合规问题。这条路暂不采用，以后可以作为节点突发故障时的备份手段。

## 三 节点生命周期：续期与换节点

- 节点到期前 3 小时先尝试续期，只申请会自动批准的短续期。
- 续期被拒，或节点已用满 7 天，就开始换节点。
- 第一次失败就告警；到期前 1 小时仍未完成，再告警一次。

## 四 选新节点：按年份加空闲，并区分失败类型

候选机型由管理员配置，按 CloudLab 硬件表的上线年份（`Circa` 列）从新到旧排列，只放 x86、不带 GPU、不需要单独审批、有 SSD 或 NVMe 的机型。

失败按看得到的信息分类：

| 现象 | 归类 | 处理 |
| --- | --- | --- |
| 创建请求返回 4xx | 配置错误 | 停止并告警 |
| 返回 401 或 403 | 凭据问题 | 停止并告警 |
| 实验在几分钟内变成 `failed`，且没有分到机器 | 可能没有空闲 | 释放后换下一个机型 |
| 已经分到机器后变成 `failed` | 装机或启动失败 | 释放、告警，再换下一个机型 |
| 同一种失败连续出现在三种机型上 | 系统性问题 | 停止并告警，不再试列表里剩下的机型 |

每次失败都把现象、机型和时间记录到操作结果里。创建失败的实验由申请操作自己释放；它从没运行过主机，不需要走释放保护。

## 五 新节点登记主机公钥

控制面第一次 SSH 到新节点前，必须已经可靠地知道它的主机公钥。信任来源是一个受保护、只能用一次的登记凭据，而不是实验名称或 UUID。

1. 开节点时，控制面生成一个随机的一次性登记凭据，只保存它的哈希。凭据绑定这次分配，有有效期（默认 2 小时），只能用来登记主机公钥，不能领取任务，也不能接管主机名。
2. 凭据以 profile 参数的形式交给 CloudLab，只出现在发出的创建请求里，不写进本地数据库的配置，也不写进日志。
3. 节点使用我们自己的 profile（放在 FAST25-AE，仅项目成员可见）开机。开机脚本读取凭据和登记地址，校验控制面的 TLS 证书，把本机的 SSH 主机公钥提交给控制面。
4. 控制面校验凭据哈希、有效期和登记状态，记下公钥，并把凭据标为已用。用同一凭据重试会得到同样的结果；想换成另一把公钥会被拒绝。
5. 申请操作等节点登记完成后，把公钥固定到节点记录里。之后所有 SSH 连接只认这把公钥，严格校验。

凭据的可见范围：

- profile 参数在 CloudLab 的实验页面上、通过 API 都能被项目成员看到。按 CloudLab 的设计，项目成员本来就能以 root 登录项目里的所有节点，所以信任范围没有扩大。
- 凭据不出现在网址、邮件和本控制面的日志里，过期或用过之后就作废。

登记成功只说明"这台机器归我们管"。接管旧主机的名字、作废旧凭据，都在第七节的切换步骤里进行。

登记接口挂在控制面对外的主 API 上，这是新的公开入口：只接受固定格式的小请求，凭据不对时统一返回同一种错误，不泄露任何信息，每次登记都写审计记录。

## 六 位子身份与数据模型

| 位置 | 字段或表 | 含义 |
| --- | --- | --- |
| `agent_compute_allocations` | `slot_host` | 本分配的节点以哪个主机名上线；为空时沿用 `compute-<节点 ID>` |
| `agent_compute_allocations` | `slot_namespace` | 沙箱命名空间（Compose 项目名）；为空时沿用 `ca-<节点 ID>` |
| `agent_compute_allocations` | `predecessor_id` | 被本分配替换的旧分配 |
| `agent_compute_nodes.connection` | `host_key` | 登记后固定的主机公钥 |
| `agent_compute_node_registrations` | 新表 | 登记凭据的哈希、有效期、状态和登记的公钥 |
| `agent_host_admission_holds.purpose` | 新增 `rotation` | 换节点期间暂停领取任务 |

说明：

- 第一个分配的 `slot_host` 和 `slot_namespace` 都为空。换节点时，新分配继承旧分配当前实际使用的主机名和命名空间。容器标签、组网桥和 nftables 表名都由命名空间派生，所以它必须保持不变。
- 主机交接：在独占锁内把主机记录的 `compute_node_id` 从旧节点改到新节点，去掉旧分配对这台主机的其他暂停，`rotation` 暂停随主机一起迁过去。之后旧节点上不再有绑定的主机，可以按原有规则释放。
- 每个位子至少准备两套部署配置（各自的隧道授权和反向端口），新旧节点轮流使用。

## 七 换节点流程

| 步骤 | 做什么 | 失败时 |
| --- | --- | --- |
| 选择节点 | 按第四节选机型，选一套空闲的部署配置，创建新分配 B，B 继承主机名和命名空间 | 没有空闲配置：停止并告警 |
| 等待节点 | 等 B 开出来、完成第五节的登记、装好 Docker 和 Kata、上传部署包。B 不登记主机、不启动服务 | 按第四节处理 |
| 预拷贝 | 旧节点 A 照常服务，把 A 的 Docker 数据预拷到 B | 重试；多次失败则释放 B，换机型 |
| 等待空闲 | 先等一个没有回合在运行的时刻；等到后立即暂停领取任务，再确认一次 | 到了排空截止时间仍不空闲，就主动排空：暂停领取，等运行中的回合结束 |
| 停止旧节点 | 停 A 上的主机服务和 Docker | 回退 |
| 补拷 | 拷贝最后的变化 | 回退 |
| 主机交接 | 数据库里把主机名交给 B 的节点 | 回退 |
| 启动新节点 | 签发主机登记令牌，在 B 上启动主机服务，以原主机名重新登记，A 的旧凭据随之作废 | 回退 |
| 确认 | 主机在线，心跳晚于令牌签发时间，broker 健康，然后恢复领取任务 | 回退 |
| 清理 | 删除 A 上的副本，释放 A | 重试；不影响用户 |

排空截止时间 = 到期时间 − 单回合上限（`AGENT_TIMEOUT_S`）− 切换所需时间（约 10 分钟）− 余量（约 30 分钟）。按默认的 1 小时上限，是到期前约 1 小时 40 分。新节点此时仍在准备，也必须暂停旧主机领取新任务，给已运行的回合留出结束时间。单回合上限调得太大、3 小时的提前量容不下时，提前告警，提示调大提前量。接近到期仍有运行中的回合时升级告警，不通过强制杀回合来推进迁移。

回退：先确认 B 上的服务已停止，再把主机名交回 A，必要时让 A 重新登记，启动 A，确认在线后恢复领取任务，然后释放 B，在下一个机型上重试。不能确认 B 已停止时保持暂停并告警，不能启动两份主机。A 上的数据在 B 确认之前不会被删除。

恢复边界：停止 A 之前先记下停止意图，避免部分停止后误以为 A 仍正常服务。B 验证通过的结果必须先持久化，再解除暂停；解除后 B 可能产生新数据，之后只能清理 A，不能回退到旧副本。清理失败保留检查点重试。备用部署配置必须与 A 的代码版本和部署包摘要一致。

用户感知：

- 排空和切换期间发出的消息显示"等待开始"，恢复后自动执行。
- 切换后的第一条消息需要冷启动，跟闲置后再使用一样。
- 正在运行的回合不会被打断。

## 八 数据拷贝

- 只拷 `/var/lib/docker` 和 `/var/lib/containerd`。不拷状态目录，凭据由重新登记生成；不拷 Kata 纪元，B 会生成自己的，只触发一次运行时重新验证。
- 由 A 直接推送到 B：`rsync -aHAXSx --numeric-ids`，停机后的最后一遍再加 `--delete`。A 使用一把只在本次换节点期间加入 B 授权列表的临时密钥，用 B 已登记的主机公钥严格校验 B。
- 必须带 `-x`（不跨文件系统）。Docker 29 使用 containerd 镜像存储时，运行中容器的合并文件系统挂在 `/var/lib/docker/rootfs/overlayfs/<容器 ID>`。不带 `-x`，预拷会把每个运行中容器的完整文件系统当普通文件再拷一遍：演练中 3 个会话多传了 7.4 GB，最后一遍还要再删掉它们。
- 分多路并行。跨站点单路只有约 30 MB/s。快照目录、镜像内容（content blobs）和其余文件都要拆开，不能留一路单独的大头。演练中 4 路快照加 1 路其余，13.5 GB 用 163 秒（83 MB/s），瓶颈是单独的那一路。
- 停机后的最后一遍也分路。演练中这一遍只传了 10 MB，但扫描约 21 GB 数据、再删掉挂载点副本，一共用了 66 秒。
- 停 A 时先停 runner，再单独停 broker，最多等 10 分钟：broker 退出时按正常流程逐个停掉还开着的沙箱，打开生命周期归档时还会上传 final。之后再并行停止剩下的容器。打开归档时，被 Docker 绕过 broker 直接停掉的沙箱会被新节点的 broker 隔离，会话无法继续。演练在归档上线之前，当时并行停止 runner、3 个 Kata 沙箱和主机服务用了 41 秒；先停 broker 会让这一步变长，打开归档时还要加上上传时间。
- 两台节点的 Docker 和 containerd 数据都放在实验的本地大盘上，用 bind mount 挂到默认路径。
- B 和 A 使用同一部署版本时，镜像和构建缓存随数据过来，启动时不需要重建。演练中 B 部署主机服务全部命中缓存，用了 43 秒。

## 九 告警

复用 `AGENT_ALERT_WEBHOOK_URL`，内容只包含事件名、主机名和原因代码；未配置时只写结构化日志。管理页在对应服务器上显示"需要处理"。

- 绑定值按 Portal 存储的字符串形式发送。

## 十二 实现顺序与验收

1. 查明 CloudLab 新建失败的原因（需要在 Portal 网页上查看）。
2. 验证一：新节点能安全地自动登记主机公钥。内容包括建 profile、凭据送达节点、确认凭据的可见范围、节点能访问控制面的 HTTPS 地址。
3. 验证二：两台节点之间整机搬家，真实会话和 Fork 都能接着使用。如果不通过，改为逐个沙箱导出导入，方案需要重新评估。2026-10-10 在 staging 上通过，结果见本节末尾。
4. 两项都通过后，实现第五至第十一节，与第十节的小修复合并为一个 PR。
5. staging 验收：
   - 强制换一次节点；
   - 跨站点换一次；
   - 故障演练：续期被拒、首选机型开不出来、切换中途失败后回退、控制面在换节点中途重启；
   - 连续两周无人值守，期间至少自动换两次节点。
6. 生产使用前，经项目负责人向 CloudLab 报备一次。

### 验证二结果（2026-10-10，staging）

做法：

- 把节点 A（Clemson r6525）作为临时主机 `cloudlab-drill` 接入 staging，用 10-08 配好的三条隧道账号。
- 在 A 上建了 Claude Code 会话、它的 Fork 和 Codex 会话，然后按第七、八节的步骤整机搬到节点 B（Utah d6515）。
- B 用同一主机名、同一命名空间重新登记。

结果：

| 项目 | 结果 |
| --- | --- |
| 会话接续 | 三个会话搬家后的下一轮都在 B 上从原生会话恢复（`warm_native`，上下文 `restored`）。 |
| 上下文 | 各自的口令都答对。Fork 记得继承的和自己的口令，原会话不知道 Fork 的口令。 |
| 文件 | 各成员家目录里的文件和 A 上写入的时间戳都在。 |
| 容器 | 容器 ID 不变。 |
| 主机不可用时间 | 共 161 秒：停 A 41 秒、最后补拷 66 秒、B 启动 Docker 5 秒、B 部署主机服务 43 秒、登记上线 6 秒。 |

由此确认：

- 同名重新登记会把主机状态重置为“登记中”，管理员的“暂停领取”随之解除。所以换节点期间必须用独立的 `rotation` 暂停（第六节），不能复用管理员的暂停。
- 第八节的拷贝要求（`-x`、多路并行、并行停容器）来自这次实测。
- 一个与搬家无关的问题也在演练中暴露：Codex 很短的回合收尾时，权限整理脚本会和 Codex 后台删除插件临时目录撞车，导致回合失败。这个问题单独修复。

## 十三 风险

- 节点突然故障（不是正常到期）时来不及搬，该节点上的会话会丢失。
- 续期被拒，同时所有候选机型长时间开不出来时，会话会丢失。
- 目前依赖个人的 CloudLab token。
